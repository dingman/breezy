## Warning — the website version trap

**nautilustrader.io serves only `latest` and `nightly`. Both are NautilusTrader 2.x. There is no version-pinned URL for 1.231.0 — every such URL 404s.** Any agent or engineer who web-searches "NautilusTrader docs", opens `nautilustrader.io/docs/...`, or fetches `llms-full.txt` is reading a **different major version** whose Python API was renamed, re-namespaced, and in places deliberately narrowed. The drift is not cosmetic: 2.x renames the actor base class, renames the entire quote/trade/book method family, moves `register_custom_data_class` into `nautilus_trader.model`, removes `self.msgbus` from the Python surface, changes the first argument of `DataType` from a class object to a string, and **states that out-of-tree Python adapters are not supported** — a claim that is false for 1.231.0, which ships a pure-Python `LiveDataClient` hierarchy, an adapter `_template/`, and a fully pure-Python Polymarket adapter. That last item is the single most expensive trap in this repo: it can talk you out of the architecture that 1.231.0 actually supports and into writing Rust you do not need. **Ground truth order for Breezy: installed wheel source > `docs/reference/nautilus/v1.231.0/` > everything on the web.**

Secondary caveat: the v1.231.0 doc tree is itself mid-migration and is **not uniformly true for the installed wheel**. Three pages carry v2-only Python import forms — `concepts/live.md`, `integrations/deribit.md`, `integrations/derive.md` (`from nautilus_trader.live import LiveNode` / `LiveNodeConfig`, both `AttributeError` in our wheel) — and `integrations/polymarket.md` documents only the Rust/PyO3 "V2" Polymarket adapter, not the pure-Python one the wheel actually ships. Sixteen v1.231.0 pages mention "Python v2" / `build-debug-v2` / `py-stubs-v2`. When a v1.231.0 doc and the installed source disagree, the source wins.

## Upgrade exposure — what breaks in Breezy on 1.231.0 → 2.x

Ranked by cost to Breezy's planned extensions. Nothing here is a reason to upgrade now; it is a reason to keep these seams thin.

1. **The entire Polymarket/Kalshi adapter, if written in Python.** 2.x deletes `LiveDataClient`, `LiveMarketDataClient`, `LiveDataClientFactory`, and `TradingNode.add_data_client_factory`, and states there is no out-of-tree Python adapter interface (issue 4694 still open as of the 2.x docs). A Python adapter is a **total rewrite in Rust** on upgrade. *Mitigation:* keep venue I/O (HTTP/WS parsing, symbol mapping, signing) in plain Python modules with no Nautilus base classes, and make the `LiveMarketDataClient` subclass a thin adapter shell. Alternatively use the PyO3 `nautilus_pyo3.PolymarketDataClientFactory` path that 1.231.0 already ships — that is the forward-compatible one.
2. **Custom weather data types.** `@customdataclass` (gone), `register_arrow` (gone), `register_serializable_type` (gone), `Data` subclassing (replaced by duck-typed `@dataclass` + five methods), and `DataType(MyClass, …)` → `DataType("MyClass", …)`. Every weather data type must be re-authored. *Mitigation:* author against the PyO3 path (`@customdataclass_pyo3` + `register_custom_data_class` + `nautilus_pyo3.DataType`) — it is the one that survives, and 1.231.0 supports it today.
3. **Every actor and strategy handler name.** `on_quote_tick`→`on_quote`, `on_trade_tick`→`on_trade`, `on_order_book_deltas`→`on_book_deltas`, `on_order_book_depth`→`on_book_depth`, `on_order_book`→`on_book`, plus the matching `subscribe_*`/`request_*` family, plus `on_historical_data` fanning out into nine typed handlers. **These fail silently** — a renamed handler simply never fires. *Mitigation:* centralize handler bodies in helper methods so the rename touches only thin dispatch stubs; add a startup assertion that each overridden handler name exists on the base class.
4. **`Actor` → `DataActor`, `ActorConfig` → `DataActorConfig`, and the config style change** (class-annotation msgspec structs → `__init__`-based). Mechanical but touches every component.
5. **Loss of `self.msgbus`.** Any Breezy component that publishes or subscribes to a custom topic directly (e.g. a weather-signal fan-out or a cross-actor coordination topic) must be re-expressed as custom data or signals. *Mitigation:* prefer `publish_data`/`publish_signal` from day one; treat `self.msgbus` as forbidden in Breezy code even though 1.231.0 offers it.
6. **`BacktestDataConfig` custom-data replay.** 2.x says custom types are not accepted and directs you to `BacktestEngine.add_data(...)`. If Breezy's backtests are config-driven via `BacktestNode` + `BacktestRunConfig` with `data_cls=WeatherObservation, metadata={...}`, that wiring is invalid post-upgrade. *Mitigation:* keep a single function that produces the backtest data inputs, so the swap to `engine.add_data(catalog.query_custom_data(...))` is one call site.
7. **`TradingNode`/`TradingNodeConfig` → `LiveNode`/`LiveNodeConfig` + builder wiring**, including `run()` vs `run_async()` semantics, `LiveNodeHandle`, and the 2.x "one node per process" restriction. Affects Breezy's live entry point and any future multi-venue (Polymarket + Kalshi) process layout — 2.x forbids concurrent nodes in one process.
8. **`ParquetDataCatalog` type/period conventions.** Class objects → string type names; `pd.Timedelta` → `period_nanos`; `nautilus_trader.persistence.catalog` → `nautilus_trader.persistence`. Affects every catalog write/query/consolidate call in the weather data pipeline.
9. **Flattened import namespace.** `test_kit`→`testkit`, `persistence.catalog`→`persistence`, `backtest.node`→`backtest`, `common.enums`→`common`, `model.data`→`model` for `OptionGreeks`/`IndexPriceUpdate`/`OptionChainSlice`. Trivial per site, large in aggregate; mostly hits test fixtures.
10. **`nautilus_trader.core.nautilus_pyo3` → `nautilus_trader._libnautilus`.** Any direct PyO3 import in Breezy is a path rewrite. Low effort, but it is exactly the mitigation path recommended in items 1 and 2 — budget for it.
11. **`CustomData` unification.** 1.231.0's two distinct `CustomData` classes collapse into one in 2.x. Code that carefully routes one or the other becomes redundant; code that assumed they were the same was already broken.
12. **New 2.x capabilities Breezy would want but cannot use yet:** `subscribe_queue_state` / `on_queue_state` (runner backpressure), `subscribe_socket_state` / `on_socket_state` / `reconnect_socket` (transport liveness), `WebSocketConfig.backend` (sockudo), `run_async()` hosted event loops. All absent from 1.231.0. Do not design around them.
