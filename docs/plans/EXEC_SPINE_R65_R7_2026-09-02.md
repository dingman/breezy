## 4. R-7 — `_submit_order` gets a body

**Null hypothesis: PARTIALLY UPHELD, and this is the increment's most important claim.** **Native, used as-is:** `LiveExecutionClient._submit_order` as the dispatch seam; `generate_order_submitted` / `generate_order_accepted` / `generate_order_rejected` / `generate_order_denied` (`execution/client.pyx`) as the event surface; `OrderDenied` as the refusal event; the `MessageBus` for delivery; `RiskEngine.set_trading_state(HALTED)`, already used by R-7-PRE. **Breezy-owned because no native exists** (parent plan, exhaustive search of 1.231.0 — zero matches for `AMBIGUOUS`/`retryable`): the durable write-ahead intent latch, the operator-permit chokepoint, the two operator-reserved caps.

**NATIVE EXISTS, DECLINED — and Revision 4 missed it entirely.** `LiveExecutionEngine._check_inflight_orders` / `_resolve_inflight_order` (`.venv/.../nautilus_trader/live/execution_engine.py:701-797`) already resolve a SUBMITTED-but-unconfirmed order: they re-query via `_query_order`, and on retry exhaustion synthesize `create_order_rejected_event(reason="UNKNOWN")` (verified at source). So the three-outcome ambiguity taxonomy is **not** a gap Nautilus left; R-4's pin `inflight_check_interval_ms=0` **disables the native resolver silently**. It is declined for two reasons, and the pin is tied to them so nobody "fixes" it by re-enabling the timer: (a) it drives resolution through `_query_order`, which is permanently in `EXEC_DECLARED_UNIMPLEMENTED_COROUTINES` here — the venue exposes no query-by-id Breezy can rely on, so the resolver has nothing to ask; (b) its exhaustion fallback **guesses REJECTED** rather than confirming it, which for a bot that must never assume itself flat is the one wrong direction — a real fill silently booked as a rejection is exactly the doubled position the latch exists to prevent. **A comment stating (a) and (b) ships beside the pin, and a test asserts the pin's value with that reason.**

**D1 — the authorization must have a CONSUMER, or the chokepoint stays inert.** `assert_live_order_submission_permitted` returns a `LiveOrderSubmissionAuthorization` whose `consume(request_fingerprint=, order_notional_usd=, now_ns=)` is the only way to spend it; today the token has **zero consumers in `src/`** (L-18's own worked example). **RECOMMEND: the write closure's first positional parameter IS the authorization**, so "never called the gate" is a `TypeError` at the dispatch site rather than a discipline question — the shape the token's docstring asks for. *Rejected:* calling the chokepoint and discarding the return (inert); returning a boolean (a value a caller can ignore). **Positional enforcement is NOMINAL in Python, so it is not sufficient on its own:** a `Mock()` with a no-op `.consume` satisfies the signature. The write closure therefore opens with an explicit `isinstance(authorization, LiveOrderSubmissionAuthorization)` guard, and the real `consume()` burns the nonce under `_REGISTRY_LOCK` (`safety.py`, `_UNSPENT_NONCES.pop`), which is what makes a second dispatch on the same token fail rather than merely look wrong.

**D2 — both caps are read on EVERY authorization, never cached.** `operator_max_daily_budget_usd()` and `operator_max_position_cost_usd()` raise on absence with no default; per-position is USD **cost** (price × quantity, rounded up to the cent), daily budget is a rolling UTC-day notional accumulator via `DailySpendLedger`. **The repo assigns neither value, anywhere.**

**The ledger over-books, verified at the code.** `DailySpendLedger.authorize_order_cost` does `self._spent_usd = self._spent_usd + cost` on a grant, and the class exposes only `spent_today_usd` and `authorize_order_cost` — **there is no release and no true-up**. A string of `DEFINITIVE_REJECT`s or partial fills therefore burns the operator's daily budget with **$0 actually at risk**, which silently converts a risk ceiling into a request-count ceiling. **Decision, conservative by default:** release the full booking on `DEFINITIVE_REJECT` (a certain non-fill); true up to `avgPx × cumQuantity` on `DEFINITIVE_ACCEPT`; **keep the full amount booked on AMBIGUOUS**, because an unresolved submit may have filled. **The release trigger, pinned now rather than left to implementation (Revision 5 named this its least-confident R-7 decision):**
