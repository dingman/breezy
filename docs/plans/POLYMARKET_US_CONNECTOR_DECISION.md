# Polymarket US Connector Decision

> Superseded for implementation sequencing by `docs/plans/POLYMARKET_US_BUILD_PLAN.md` (2026-08-25). This document remains evidence for rejecting a repointed `.com` adapter, but the build plan now owns phase order, safety gates, and open questions.

## Verdict

No. The shipped NautilusTrader Polymarket adapter can be given a different host, but direct evidence shows it is a `.com` global-CLOB adapter whose downstream protocol is coupled to Polygon wallet identity, CLOB `POLY_*` HMAC/EIP-712 authentication, condition/token identifiers, CLOB order wire bodies, and `/ws/market`/`/ws/user` websocket messages. Polymarket US exposes different public/authenticated hosts and, in the official `polymarket-us` 0.1.2 SDK, signs `X-PM-*` Ed25519 key-id requests against `/v1/...` paths and trades by `marketSlug`/intent. Repointing the endpoint is therefore insufficient; the viable Nautilus-native path is a separate `polymarket_us` adapter built on Nautilus extension classes, reusing the official US SDK only as transport until contract tests prove it insufficient.

## Options

| Option | Rough effort | Trade-offs | Viability |
|---|---:|---|---|
| A. Repoint shipped adapter | 0.5-2 days to try; likely fails immediately | Preserves upstream code superficially, but collides with auth headers, order payloads, websocket schema, identifier model, and custody assumptions. Any "fix" quickly becomes a rewrite inside `.com` adapter code. | Not viable. Evidence above classifies core transport/execution/data paths as structural. |
| B. Build `polymarket_us` Nautilus adapter wrapping official `polymarket-us` SDK | MVP 8-15 engineering days; production hardening 3-5 weeks | Preserves Nautilus immutability and native extension model; reuses official venue transport; easier to swap later for Kalshi-style exchange adapter. Risk: SDK 0.1.2 may lag docs, especially websocket field casing; contract tests must detect drift. | Recommended. |
| C. Build `polymarket_us` adapter with hand-rolled transport | MVP 12-20 engineering days; production hardening 4-6 weeks | Avoids SDK lag and gives exact control over schemas/retries/observability. Higher implementation and auth risk; more surface to maintain as US docs change. | Viable fallback if SDK contract tests fail. |
| D. Build against Polymarket US institutional exchange API/FIX/gRPC instead of retail SDK | Discovery 1-2 weeks after access; adapter 4-8+ weeks | More exchange-native and potentially better for professional trading, but requires onboarding, Auth0 Private Key JWT, participant/account IDs, scopes, and possibly gRPC/FIX stream semantics. | Open pending operator access/model choice. |

## Recommendation

Choose Option B first, with a fail-fast SDK contract-test gate. This honors the Breezy priority order: it leaves Nautilus immutable, uses Nautilus's adapter extension classes instead of patching the shipped `.com` adapter, favors correctness over a brittle endpoint substitution, keeps risk visible before trading, and produces an exchange-shaped boundary that can later inform Kalshi integration. If SDK 0.1.2 fails against current docs or live unauthenticated/authenticated sandbox contracts, fall back to Option C for transport only; keep the Nautilus adapter boundary unchanged.

| 3.
