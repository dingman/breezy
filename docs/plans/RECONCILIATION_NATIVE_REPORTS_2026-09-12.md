## 3. Design

**Where.** Only `src/breezy/adapters/polymarket_us/exec/client.py` (two generator bodies, two write sites, one memoised read helper, one record dataclass), plus ONE config field in `src/breezy/strategy/current_rung_hold/composition.py` if ruling R2 says claim.

**Inputs.** The venue's `PORTFOLIO_POSITIONS_PATH` page already read for position reports (read ONCE per mass-status pass, memoised under an `asyncio.Lock`, invalidated when `reconciliation_active` goes False) + the durable fill records reached by `slug → _find_instrument → fill_records_for`. **No new index key is needed** — the positions page supplies the instrument ids the store cannot enumerate (it has no prefix scan, `exec/client.py:2331-2350`).

**Gating rule (load-bearing).** A durable record is reported **iff the venue currently reports an open position for its instrument**. Reporting unconditionally would assert a LONG the venue no longer holds after settlement — a phantom that does NOT exist today, i.e. a regression. The reports are a corroboration of the same evidence the position report carries, never an independent claim.

**Outputs per record.** `OrderStatusReport(account_id, instrument_id, venue_order_id, order_side=BUY, order_type=LIMIT, time_in_force=IOC, order_status=FILLED, quantity=<record.orderQty, else cumulative_qty>, filled_qty=cumulative_qty, avg_px=price=cumulative_cost/cumulative_qty, client_order_id=<record>, ts_accepted=ts_last=ts_event)` and `FillReport(same ids, trade_id=<record.tradeId, else GET-<venue_order_id>>, last_qty=cumulative_qty, last_px=avg_px, commission=<RULING R1>, liquidity_side=TAKER, ts_event)`. **Unit declaration (L-2):** `quantity` is the TERMINAL FILLED PORTION when `orderQty` is absent, not the original order size; an IOC's unfilled remainder is venue-cancelled, so a `FILLED` terminal is faithful for position purposes and understates only the original intent. B0 removes the ambiguity for every record written after it.

**Fill reports are only reachable through an order report.** `_reconcile_execution_mass_status` iterates `mass_status.order_reports.items()` and looks fills up by that order's `venue_order_id` (`live/execution_engine.py:1880-1881`); there is no fill-only loop. An orphan `FillReport` is silently ignored — so `generate_order_status_reports` MUST be implemented together with `generate_fill_reports`, not after it.

**NOT changed (byte-unchanged pins, by test name).** `classify_create_order_outcome` and `test_an_ambiguous_outcome_keeps_the_latch_open_and_does_not_release_the_booking["200-id-no-exec"]` (PREREG v3 §4a/L-36); `test_the_settlement_landmine_stays_disarmed_only_while_the_position_check_is_off`; `test_a_flat_venue_report_on_a_held_long_is_never_forwarded`; `test_a_client_returning_none_fails_reconciliation`; `test_the_report_generators_never_raise_into_the_native_handler`; `test_a_position_matching_a_durable_fill_record_is_priced_from_it`; every duplicate-fill test in `tests/unit/test_current_rung_hold_trial_day_latch.py`; `_submit_order`'s eight gates (`exec/client.py:2647-2716`); `calculate_commission` (`:2513-2570`).
