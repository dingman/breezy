## §1 Null-hypothesis verdict: Nautilus does NOT cover this

Confirmed against `nautilus_trader==1.231.0` (`.venv/lib/python3.13/site-packages/nautilus_trader-1.231.0.dist-info`) and the repo's own prior investigation, not re-litigated:

- `docs/reference/nautilus/digests/adapters-live-networking.md:158-161`: `LiveDataEngine.connect()`/`disconnect()` iterate clients **once**; zero `reconnect`/`resubscribe` hits across `live/*.py` + `data/engine.pyx`. No engine-level reconnect loop or watchdog exists.
- `:171-217`: Nautilus's **socket**-level auto-reconnect (`nautilus_pyo3.WebSocketClient`/`WebSocketConfig` backoff+jitter+`reconnect_max_attempts`) is real but adapter-authored re-subscription is still required, and — per `src/breezy/adapters/polymarket_us/websocket.py:3-15` — Breezy explicitly rejected the native pyo3 reconnect for the markets socket because `WebSocketConfig.headers` are fixed at construction and can't re-sign per reconnect; Breezy's own `PolymarketUSMarketsWebSocket(Pool)` owns socket reconnection instead. That reconnect already worked on 09-14 (the recorder, sharing the same socket layer, reconnected within minutes).
- The actual failure is one layer up: Breezy's own `PolymarketUSDataClient._feed_watchdog` (`src/breezy/adapters/polymarket_us/data.py:1028-1030,1910-1949`) treats a degraded/dead feed as **fatal** and calls the native `Component.shutdown_system()` — itself the correct native primitive (`feed_fault.py:8-14`) — which stops the whole `TradingNode`. Nautilus supplies the shutdown mechanics; it supplies **no** mechanism to bring the node back. `TradingNode.run()` returns `None` either way (`data.py:1893-1897`).
- **Verdict: a supervisor-level relaunch is still necessary.** Nothing in Nautilus 1.231.0 restarts a dead `TradingNode` process; that is process supervision, which is explicitly outside Nautilus's scope and is Breezy's own `trade_supervisor.py`.

## §2 Root cause (three independent gaps, not one)

1. **Scheduler never re-arms.** `next_due` (`src/breezy/runtime/trade_supervisor_core.py:556-587`) only returns `Phase.RELAUNCH_CHECK` while `LAUNCH_UTC(16:50) <= t < LAUNCH_WINDOW_END_UTC(17:00)`. After `SELF_CHECK_WINDOW_END_UTC` (17:10, `:45`) the loop returns `Phase.NONE` for the rest of the day (`_run_forever`, `trade_supervisor.py:1201-1203`) — nothing polls `tracked_pid` liveness again until tomorrow's `STOP_PRIOR_UTC`. The node died at 19:57Z into total silence.
2. **[E4]'s readiness gate is checked FIRST, unconditionally.** `decide_relaunch` (`trade_supervisor_core.py:389-390`): `if readiness_was_observed: return RelaunchDecision(False, ...)`. This node achieved readiness at boot (it traded fine for 3 hours), so even a re-armed check would have declined. [E4]'s own name for this ("zero attempts once readiness was ever observed") is a **boot-window** heuristic — it assumes a crash after readiness means a repeat of a non-deterministic startup race, not a fresh mid-day network event 3 hours later. That assumption does not hold mid-day.
3. **Cause classification would also have declined it.** `classify_exit1_cause` (`:352-360`) only recognizes `PERMIT_NOT_ISSUED_MARKER` ("order submission permit not issued" → DETERMINISTIC) and `TRADING_NODE_FAILED_MARKER` ("trading node failed" → TRANSIENT, only logged on an uncaught `BaseException`, `trade_cli.py:434-435`). A fatal-feed-fault shutdown is a **clean** `node.run()` return, not an exception — it logs `"breezy-trade: FATAL market-data fault in ...: ... shut down."` (`trade_cli.py:220-224`; exec-fault sibling print at `:206-210`). Neither existing marker matches either literal, so `classify_exit1_cause` would return `UNKNOWN`, and `decide_relaunch` declines on anything `is not RelaunchCause.TRANSIENT` (`:393-394`) — UNKNOWN included.

None of these three is a mistake in [E4] itself — [E4] is correct for the 16:50-17:00 boot window it was designed for. The gap is that nothing analogous exists for 17:10Z-01:00Z(+1) (§3 moves the open edge from 17:00 to 17:10).

## §3 Design: a separate MID-DAY relaunch budget

### Cause classification, with drain-safe latching

Two new markers in `trade_supervisor_core.py`: `FATAL_MARKET_DATA_FAULT_MARKER = "FATAL market-data fault"` (substring of the `print()` at `trade_cli.py:220-224`; the identical substring also appears in `quote_tape_cli.py:169` for the recorder's own CLI — harmless, that process writes a different log file the supervisor never reads) and `FATAL_EXEC_CLIENT_FAULT_MARKER = "FATAL execution-client fault"` (`trade_cli.py:206-210`). Extend `classify_exit1_cause`: `PERMIT_NOT_ISSUED_MARKER` first (unchanged, still wins — DETERMINISTIC), then `TRADING_NODE_FAILED_MARKER` (unchanged), then **new**: either fatal-fault marker → `TRANSIENT`. Purely additive — no existing branch's precedence changes, so [E4]'s boot-time DETERMINISTIC classification is untouched (also closes the boot-window version of the same gap for free).

The FATAL line is printed once, at shutdown, and the child may take real wall-clock time to actually exit afterward (clean-stop teardown — `StreamingFeatherWriter.close()` before the exit status is authored, `data.py:1893-1897`) — so the poll that first sees the marker is not reliably the SAME poll that first sees the process dead, and `IncrementalLogReader`'s offset-draining `read_new` (`:489-506`, 256-byte carry) can drain past the marker text before death is observed — exactly the `strategy_subscribed_seen`/`permit_issued_seen_expires_at_ns` bug already fixed for boot (core.py:651-678, "fix 2026-09-05"/"fix 2026-09-06"). Amend with the same pattern: new `DaySchedulerState.midday_cause_seen: RelaunchCause | None = None`, and `record_midday_cause_seen(state, cause)` (first-seen-wins, mirrors `record_permit_issued_seen`'s idempotency at `:666-678`). `_do_midday_watch` calls `classify_exit1_cause` against **every** poll's log delta, alive or not, and latches the first non-`UNKNOWN` result immediately. At death-detection time: `cause = state.midday_cause_seen if state.midday_cause_seen is not None else classify_exit1_cause(log_text)` — latch OR live delta, never live delta alone.

### Liveness that distinguishes zombie from running

`process_is_alive` (`trade_supervisor.py:453-460`) is `os.kill(pid, 0)`, which succeeds for a **zombie** (the kernel keeps the PID entry until reaped) exactly as it does for a running process. `spawn_node` (`:563-590`) returns a `subprocess.Popen`, but every caller keeps only `.pid` — no code anywhere calls `.poll()`/`.wait()`/`os.waitpid`. This function is the single `SupervisorPorts.process_alive` port (`:699-729`, field `:705`, wired at `:729`) shared by `_do_relaunch_check` (`:936`), `_do_self_check` (`:1007`), and `terminate_after_toctou_recheck` (`:445-450`) — so today's boot-time RELAUNCH_CHECK/SELF_CHECK already have this bug; a dead-but-unreaped child at boot would already be misreported "alive" forever. Fixing the shared port fixes all callers at once, including the new `_do_midday_watch`.

Fix, in the port itself, not duplicated per caller: add `_proc_state_char(pid) -> str | None`, reading `/proc/<pid>/stat` and parsing the state field **after the last `)`** (the `comm` field can itself contain spaces or parens, so a naive whitespace-split is wrong) — returns `None` if the file is unreadable/absent. Amend `process_is_alive`:
```
def process_is_alive(pid: int) -> bool:
    try:
        os.kill(pid, 0)
    except ProcessLookupError:
        return False
    except PermissionError:
        return True
    return _proc_state_char(pid) != "Z"
```
**Adoption path**: a PID this supervisor did not spawn (adopted via `_attempt_adoption`, `:790-805`, after a supervisor restart finds a live flock holder) has no `Popen` object in this process, so `waitpid`/`Popen.poll()` are unavailable — `os.kill(pid, 0)` + `ECHILD` on any wait attempt would tell us nothing more than existence. `/proc/<pid>/stat`'s state field needs no parent relationship, only read access (the same access `_process_start_time`, `:528-534`, already relies on) — so the SAME check covers a supervisor-spawned child and an adopted PID uniformly; no adoption-specific branch is needed. If an adopted PID becomes a zombie, reaping it is its **real** OS parent's job (whichever process actually forked it, possibly a since-exited prior supervisor instance now reparented to init) — not this process's responsibility; the fixed liveness check still correctly reports it dead via `/proc` state regardless of who eventually reaps it.

This also un-inverts an earlier draft's reaping claim: reaping-on-next-`Popen()` (CPython's own `subprocess._cleanup`) was never reachable before, because `process_is_alive` never returned `False` for our own dropped zombie — the relaunch path was never entered. Fixing liveness is the precondition; the reaping mechanism itself needed no change.

**Side effect on `terminate_after_toctou_recheck` (STOP_PRIOR path).** For a zombie prior-day node, today's buggy `alive_check` reports "alive," falls through to the holder check, and raises `StopPriorRaceRefused("pid no longer holds the intent flock")` (`:448-449`) — the flock is already released at process exit, before the zombie state. After the fix, `alive_check` correctly reports dead and raises `StopPriorRaceRefused("pid no longer exists")` (`:446-447`) instead. Same fail-closed outcome (STOP_PRIOR still refuses and alerts), different alert text — a real, benign behavioral side effect of the shared-port fix, tested explicitly (§4).

### Phase ordering: MIDDAY_WATCH never starves SELF_CHECK

`next_due` (`:556-587`) checks phases in order: STOP_PRIOR (`:571-572`), LAUNCH (`:574-575`), RELAUNCH_CHECK (`:577-582`), SELF_CHECK (`:584-585`), then the `Phase.NONE` fallback (`:587`). The new `MIDDAY_WATCH` branch is inserted **after** SELF_CHECK's branch and **before** the fallback — and, independently, its window **opens at `SELF_CHECK_WINDOW_END_UTC` (17:10Z)**, not at readiness, so it cannot become due before SELF_CHECK's own 17:05-17:10 window closes even if readiness/permit/subscription all land early:
```
watch_open_at  = _at(effective.day, SELF_CHECK_WINDOW_END_UTC)   # today's trading day, 17:10Z
watch_close_at = midday_watch_window_end(effective.day)          # trading_day + 1 day @ 01:00Z
if effective.launch_done and effective.readiness_observed and watch_open_at <= now_utc < watch_close_at:
    return Phase.MIDDAY_WATCH, watch_open_at
```
Both endpoints compare a full `datetime`, not a bare `.time()`, because the close side crosses UTC midnight (a `.time()`-only check would wrongly exclude the 00:00-01:00Z LAX/SFO tail). A death in the 17:00-17:10Z gap (RELAUNCH_CHECK closed, MIDDAY_WATCH not yet open) is caught by SELF_CHECK's own existing `child_alive` check (`:1007`, `SELF_CHECK_FAIL_CHILD_EXITED`) exactly as today — unchanged, not a new gap.

### Relaunch bookkeeping keeps the per-child latches; bounded post-relaunch readiness check

Because MIDDAY_WATCH cannot become due before `self_check_done` is already latched `True`, a mid-day relaunch's latch-clearing can never retroactively flip a SELF_CHECK verdict — SELF_CHECK has already run and finished. `_do_midday_watch` still **keeps** reading `STRATEGY_SUBSCRIBED_MARKER` and the permit-issued line on every poll and latching them via the existing `record_strategy_subscribed_seen`/`record_permit_issued_seen` (`:651-678`, reused, not duplicated). `record_midday_relaunch_attempt` (new, mirrors `record_relaunch_attempt`, `:633-643`) calls `record_child_adopted` (`:619-630`) to clear `strategy_subscribed_seen`/`permit_issued_seen_expires_at_ns`/`midday_cause_seen` for the new child — `readiness_observed` itself is never cleared (sticky for the whole trading day, same as today), so MIDDAY_WATCH's own gate stays satisfied across a relaunch.

Those fresh latches feed a **bounded post-relaunch readiness re-check**, reusing the B3 three-way conjunction verbatim (`readiness_observed(*, holds_intent_lock, permit_issued, strategy_subscribed)`, `core.py:342-349`) — never reimplemented. New constant `MIDDAY_READINESS_RECHECK_TIMEOUT = 2 min`, anchored at `last_midday_relaunch_attempt_at`. If the conjunction is not satisfied within the timeout and the process is still alive (a still-dead process is already handled by the ordinary decide/decline path), alert once via a new `AlertDetail.MIDDAY_RELAUNCHED_CHILD_NOT_READY` — observability only, never a forced extra relaunch (that risks a runaway loop against the same budget).

### Exhaustion state and the tracked_pid contract

New `DaySchedulerState.midday_alert_sent: bool = False`, set the first (and only) time `decide_midday_relaunch` declines with the budget exhausted, gating `AlertDetail.MIDDAY_RELAUNCH_EXHAUSTED` to fire exactly once. **Contract, explicit and opposite to boot's**: on any midday decline — mid-budget or exhausted — `_do_midday_watch` returns the **same** `tracked_pid` it was given, never `None` (contrast `_do_relaunch_check`'s `:949 return None, node_log, state` on its own decline, correct for boot since that window is genuinely over). Keeping the dead PID visible names it in every subsequent `log_decision` line for operator diagnosis, and gives `_do_midday_watch` a stable non-`None` value to re-enter on every remaining poll of the day. Once `midday_alert_sent` is `True`, `_do_midday_watch` short-circuits before any log read/reclassification — otherwise it re-does full decision work every 60s for the rest of the day for no purpose.

### Dropped per-poll flock probe

`_do_relaunch_check` calls `ports.resolve_intent_lock_holder(...)` (`:927`) on **every** poll to feed `holds_intent_lock`. `_do_midday_watch` only needs that probe during the bounded post-relaunch readiness re-check above (a few polls, once per relaunch) — a steady-state "is the already-ready node still alive" poll never needs it. Over a ~7h50m watch window at the 60s `_SCHEDULE_POLL_INTERVAL_S` cadence that is roughly 470 polls/day; gating the flock probe to only the recheck window removes ~470 pointless `/proc/locks` reads/day in the common (no-incident) case.

### Down-all-day coverage

A node that never reaches readiness at all (boot-time failure) gets zero coverage from `MIDDAY_WATCH` — its gate requires `effective.readiness_observed`, which such a node never sets. That case stays entirely [E4]'s (boot-time RELAUNCH_CHECK's) responsibility, unchanged.

## §5 Deploy

`systemctl --user restart breezy-trade-supervisor.service`. Safe at any time: the node runs detached (`start_new_session=True`, `trade_supervisor.py:587`) in its own session, so restarting the supervisor never touches a live child — on its next `LAUNCH`/`STOP_PRIOR` phase the restarted supervisor re-discovers and **adopts** any live node via the existing flock-probe path (`_attempt_adoption`, `:790-805`, `LaunchAction.REFUSE_LOCK_HELD` branch, `:833-848`), unchanged by this plan. Prefer restarting outside the 16:40-17:10Z boot/self-check window purely to avoid interleaving with that narrow, timing-sensitive sequence — not a correctness requirement. Verify: `journalctl --user -u breezy-trade-supervisor -f` shows the unit restart, then (same day, after 17:10Z) no `phase_exception_contained` lines; on the next incident, `journalctl` should show a `relaunching` (or `relaunch_declined`) `log_decision` line tagged from the MIDDAY_WATCH path within one poll of the dead-feed shutdown, and `systemctl --user status breezy-trade-supervisor` stays `active`. If the dead node had an in-flight order at the moment of death, the relaunched node's own boot-time intent reconciliation may find the prior child's submit intent left **OPEN** and refuse account-wide (`submit_intent.py:1-19,365-421`) — this is the pre-existing, already-documented behavior, not a new bug; the operator clears it with the existing `breezy-clear-submit-intent` tool (`src/breezy/runtime/clear_submit_intent_cli.py:69`).

**Verified and closed by citation.** `DailySpendLedger.authorize_order_cost` (`operator_controls.py:347`) already re-keys on a **live, non-restarted** node: `if self._day != day: ... self._day = day; self._spent_usd = Decimal(0)` (`:402-416`), computed from `utc_day_for_ns(now_ns)` lazily on the next order attempt after UTC midnight. `_seed_spend_from_durable_fills` (`exec/client.py:1292-1360`) re-seeds `DailySpendLedger.seed_spent` and `seed_permit_budget_from_prior_spend` at every boot (including a relaunch), summing only fill records whose `ts_event` falls in **today's** UTC day (`:1349`, `today` computed at `:1325`) and calling `seed_spent` at `:1355`. A relaunch at 00:10Z therefore seeds the new UTC day's ledger from real durable fills (possibly zero, if none yet) — **consistent** with what the same running node would do on its own very next order attempt; a relaunch does not lose or re-grant budget relative to not restarting at all. Corroborating: the durable `is_day_budget_exhausted(utc_day)` marker (`trial_day_latch.py:812-824`) is itself keyed by a `YYYY-MM-DD` UTC calendar day and persists in the durable store, independent of any process's lifetime — the same UTC-day design the in-memory ledger's re-key mirrors. `R8_OPERATOR_RUNBOOK.md:217`'s claim that a restart "resets the per-process daily ledger and session budgets" is stale in light of the boot-time re-seed and is corrected in §4 step 8, not here.

## §7 Risks

- **Trading-day rollover fix touches 7 raw-date sites** (6 `_for_day` calls + `initial_scheduler_state`) plus one dependent fix in `_next_scheduled_event` (the `effective.day != today` special case, §4 step 3) — the widest blast radius here. Guarded by dedicated RED tests run in isolation before any other change lands, plus the pre-swap grep for sub-16:40Z fixtures (§4 step 1).
- **Zombie liveness fix changes a 4-caller shared port** (`_do_relaunch_check`, `_do_self_check`, `terminate_after_toctou_recheck`, plus the new `_do_midday_watch`), including a benign alert-text change on `terminate_after_toctou_recheck`'s zombie-prior-node path (`:446-447` vs `:448-449`, §3). Guarded by `test_a_zombie_child_is_not_alive`, `test_a_running_child_is_still_alive`, and `test_stop_prior_refuses_a_zombie_pid_with_the_nonexistent_reason` (§4 step 2), each exercising the port/caller directly.
- **Marker-drain misclassification**: guarded by `test_a_fatal_marker_seen_two_polls_before_death_still_classifies_transient`, the exact 09-05/09-06 failure shape replayed against the new markers.
- **Crash-loop risk**: a deterministic mid-day failure that logs neither fatal-fault marker (OOM kill, segfault, no application log at all) classifies `UNKNOWN` and is correctly declined — fail-closed, matching [E4]'s own default. Test: `test_midday_never_relaunches_an_unknown_cause`.
- **Double-scheduling at the 17:10 boundary**: guarded by `test_self_check_still_wins_at_1705_with_readiness_observed` and by construction (MIDDAY_WATCH's window cannot open before `self_check_done` latches).
- **Silent phase mis-dispatch**: a future third new `Phase` landing in the bare `else` would silently run `_do_self_check`. Guarded by the defensive final `else` + `test_run_forever_never_routes_midday_watch_into_self_check`.
- **A relaunched child re-taking a station-day**: guarded by the already-durable `TrialDayLatch` (§6); the midday integration test (§4 step 6) additionally asserts a fake dead-feed-kill-and-relaunch produces exactly one trial per station-day.
- **Exhausting the mid-day budget silently, or re-alerting every poll for the rest of the day**: guarded by `midday_alert_sent` + `test_do_midday_watch_declines_and_alerts_on_exhaustion_exactly_once`, and by the post-alert short-circuit.
- **A relaunched child that never becomes ready** (stuck handshake, silent block): guarded by `test_do_midday_watch_alerts_when_relaunched_child_never_readies` — observability only, does not consume an extra relaunch attempt.
- **An adopted zombie this process cannot reap**: harmless — it is not this process's child; the fixed liveness check still reports it dead regardless of who reaps it (§3).
