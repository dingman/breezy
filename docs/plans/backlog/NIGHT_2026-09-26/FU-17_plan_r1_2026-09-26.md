## Scope

**In scope (design + plan only — no code, no venue calls, no live/systemd touch):**
- Why the four observed FU-17 zero-instrument refusals each cost a *whole* trading day, not just the 16:50–17:00Z window.
- How `_do_relaunch_check`/`_do_midday_watch`/`next_due` classify and gate a relaunch today, and the exact wiring gap that causes the loss.
- A recommended, bounded, catalog-readiness-gated boot-retry design, its ACs, file-by-file plan, RED tests, and risk register.

**Explicitly out:** implementation, the A1 halt (stays operator-only, untouched by this design), `allow_short`, operator caps, permit-issuance semantics beyond the one new call site reusing existing issuance, and any change to what the node evaluates/decides once running.

## L-1 null-hypothesis verdict

Confirmed against installed capability, not invented: the catalog read this design needs already exists natively — `ParquetDataCatalog(catalog_root).instruments()`, used today at `src/breezy/strategy/current_rung_hold/composition.py:337-339` (`_read_catalog_instruments`). No new catalog-scanning code is proposed; the plan reuses this one call through a thin, exported wrapper. Nautilus itself offers no relaunch/retry/scheduling primitive — that machinery (`Phase`, `next_due`, `DaySchedulerState`, `decide_relaunch`) is already Breezy's own extension in `src/breezy/runtime/trade_supervisor_core.py`, so the gap is closed by extending that existing extension point, never by building a parallel scheduler.

## Root cause (measured, not assumed)

1. `NoTradableInstrumentsError` is a `SettingsError` subclass (`composition.py:166-171`), raised at `composition.py:645-646` when every station resolves 0 instruments. `app/trade.py::run`'s broad `except (SettingsError, OSError, ...)` (lines 616-640) and `_report(...)` return `EXIT_CONFIG_ERROR = 2` (`src/breezy/runtime/cli.py:69-71,104-117`). `_report` **unconditionally prints** `breezy: configuration error: current_rung_hold: resolved 0 instruments for <date> (...); refusing to start` to stderr — and `spawn_node` redirects `stderr=subprocess.STDOUT` into the node log (`trade_supervisor.py:711-738`), so this exact text always lands in the log the supervisor tails, independent of logging level.
2. `_do_relaunch_check` classifies the dead child purely by log-text markers via `classify_exit1_cause` (`trade_supervisor_core.py:518-531`): it only recognizes `PERMIT_NOT_ISSUED_MARKER`→DETERMINISTIC, `TRADING_NODE_FAILED_MARKER`/`FATAL_*`→TRANSIENT, else **UNKNOWN**. The zero-instrument text matches none of these, so `cause=UNKNOWN`, and `decide_relaunch` (`trade_supervisor_core.py:549-570`) declines with `"exit cause is not transient"` — exactly the observed log line.
3. **Structural finding (the actual "whole day lost" cause):** `next_due` only returns `Phase.MIDDAY_WATCH` when `effective.launch_done and effective.readiness_observed` (`trade_supervisor_core.py:1023-1028`). Once RELAUNCH_CHECK's budget (≤2 attempts, ≥3 min apart, hard cutoff 17:00Z) is exhausted with readiness never observed, `next_due` returns `Phase.NONE` for the **rest of the day** — `Phase.MIDDAY_WATCH` never becomes due at all. `_do_midday_watch` itself also early-returns whenever `tracked_pid is None` (`trade_supervisor.py:1259-1260`), so even if it *were* dispatched it would do nothing. Fixing only the classifier (item 2) therefore helps only lags shorter than ~10 minutes; it cannot fix the measured incidents.
4. `disambiguate_exit_config_error`/`ExitConfigErrorCause` (`trade_supervisor_core.py:534-540`, doc-commented "[R7b] exit-2 is read off the intent flock ... free -> config error (retryable once before 17:00 UTC)") is **dead code**: `grep` across the whole repo shows its only callers are its own two unit tests (`tests/unit/test_trade_supervisor.py:502,505`). R7b's intended exit-2 retry was designed but never wired into `_do_launch`/`_do_relaunch_check`/`_do_midday_watch`. This is a second, independent gap this design should close or explicitly supersede rather than leave stranded.
5. Ingest cadence is `OnCalendar=*:0/15` (`deploy/systemd/breezy-quote-tape-ingest-frequent.timer:21`) — a 15-minute healing cycle, confirming L-49's framing. L-49 (`docs/core/LESSONS.md:1543-1557`) also records that the *ingest-side* memory-ceiling root cause is now largely fixed (ING-2 S1/S2/S3a delivered 2026-09-25/26) — so post-fix stalls should be shorter/rarer, which argues for a **modest, bounded** retry rather than a large scheduler rewrite.

## Acceptance Criteria

1. A boot whose log carries the zero-instrument marker text and whose LAUNCH+RELAUNCH_CHECK budget exhausts without readiness is latched as `RelaunchCause.TRANSIENT`, distinct in a unit test from every DETERMINISTIC/UNKNOWN case.
2. With `readiness_observed=False` at 17:00Z and a latched boot cause of TRANSIENT, `next_due` returns `Phase.MIDDAY_WATCH` from 17:10Z onward (not `Phase.NONE`).
3. With the same state but a latched cause of DETERMINISTIC or UNKNOWN, `next_due` still returns `Phase.NONE` — a genuine config error or an unclassified failure never enters boot-retry.
4. A read-only catalog check reporting zero day-D instruments for every configured station consumes **zero** attempts and issues **no** spawn.
5. A catalog check reporting ≥1 day-D instrument for ≥1 station triggers exactly one bounded `ports.spawn(...)`, gated by the same lock/PID/adoption precheck `_do_launch` already performs (`decide_launch_action`, `_attempt_adoption`).
6. The boot-retry budget is its own counter: ≤3 attempts, ≥5 minutes apart, never at/after `midday_watch_window_end` (01:00Z) — independent of `relaunch_attempts` and `midday_relaunch_attempts`.
7. Attempt-budget exhaustion and window-close-while-never-ready each alert CRITICAL exactly once per day, via two distinct `AlertDetail` values.
8. A boot-retry child that reaches readiness latches `readiness_observed=True` through the existing path; from then on the existing `readiness_observed`-gated MIDDAY_WATCH branch polls it — no new post-readiness code.
9. A boot-retry child mints its own, unrestricted first-boot permit exactly like a normal 16:50Z LAUNCH — never clamped by `first_boot_permit_expires_at_ns` (there is none; no earlier boot succeeded today).
10. A transient catalog-read error (e.g., concurrent writer) is treated as "not ready," logged (not alerted) unless it recurs, and never crashes the phase.
11. No file under `strategy/current_rung_hold/{decision,exit_decider,exit_authorization,tick_eval}.py`, `runtime/order_enablement.py`, or the A1 halt read path changes.
12. New `AlertDetail`/state fields are pure additions; any exact-set pin test widens by exactly the new reviewed rows (L-12).

## Edge Cases & NFRs

- **Venue genuinely stopped listing (permanent zero):** catalog check never reports ready → zero attempts spent → 01:00Z close → CRITICAL "catalog never became ready," clearly distinct from "attempts exhausted." Day correctly loses no trades — same fail-closed outcome as today, better diagnosed.
- **Duplicate-boot / adopted-live-node race:** boot-retry MUST reuse `decide_launch_action`/`_attempt_adoption`, never call `ports.spawn` directly — prevents a second node under a supervisor restart or an already-live adopted child.
- **Flapping catalog mid-check:** wrap the read so a `CatalogPathError`/parquet I/O hiccup degrades to "not ready," not an exception that spends `phase_exception_contained` noise every 5 minutes.
- **Loudness without spam:** per-poll `log_decision` always; alert only at state transitions (first entry, each consumed attempt already logged at INFO, exhaustion/window-close CRITICAL) — mirrors the existing `midday_alert_sent` once-per-day gate shape.
- **A1 halt / operator caps:** orthogonal — the halt is read by strategy code at runtime, never by the supervisor's launch decision; this design adds no new caller of it and does not touch `operator.env`.

## Design & Data Flow — options considered

- **(a) Marker→TRANSIENT only, retried inside the existing RELAUNCH_CHECK budget.** Trivial, zero new state, fully reuses `decide_relaunch`. **Insufficient alone**: bounded to ≤2 attempts inside a 10-minute window (16:50–17:00Z) that closes before most observed ingest lags heal, and does nothing about the structural `next_due` gate (§Root cause item 3) — the day is still lost for any lag >~10 min.
- **(b) Gate relaunch purely on catalog readiness, no cause distinction.** Strongest anti-mask property, but standalone it says nothing about *when* to poll or how to bound attempts, and — critically — if wired to fire for *any* exit (not just zero-instrument transient), it would retry a genuine config error whenever the catalog happens to look ready, silently masking a real defect. Rejected as a standalone mechanism.
- **(c) Ingest-completion event triggers a relaunch.** Requires new signaling infra between the ingest systemd timer and the supervisor (a new coupling and a new failure mode: "the trigger itself was lost"). Nautilus and systemd offer no native hook for this; building one violates YAGNI/native-extension-first when the supervisor already polls everything else on a 60s cadence. Rejected.
- **Recommended: (a) + (b) composed, inside the existing MIDDAY_WATCH window.** Cause-gated (only zero-instrument-classified TRANSIENT boots enter this path — closes the R7b gap in a way that can never retry a DETERMINISTIC/UNKNOWN exit) **and** readiness-gated (an attempt is only *spent* when the catalog shows real day-D progress, so a permanently-empty catalog burns zero attempts rather than thrashing) **and** budget/window-bounded (its own small, independent counter, capped by the existing `midday_watch_window_end`=01:00Z). This is a poll, matching the supervisor's existing idiom exactly, and needs no new infrastructure.

## Risk Register

| Risk | Mitigation |
|---|---|
| Boot-retry double-spawns alongside an adopted live node | Reuse `decide_launch_action`/`_attempt_adoption` verbatim rather than a bare `ports.spawn` (AC5). |
| Marker text drifts if `_zero_instruments_message` is edited later | Import the constant from `composition.py` rather than re-literalling it in `trade_supervisor_core.py` — one definition. |
| Boot-retry masks a real config error by retrying too broadly | Gated strictly on `boot_cause_seen is TRANSIENT`, which is itself gated on the exact zero-instrument marker only — DETERMINISTIC/UNKNOWN never reach this branch (AC3, regression-pinned test). |
| Catalog check gives a false "ready" on a partial/mid-write parquet snapshot | This is a read of the same primitive `_read_catalog_instruments` already trusts for the real boot — no weaker guarantee than today's boot-time check; a false-ready simply reproduces today's normal zero-instrument refusal on the next boot, re-entering the same bounded loop, not worse. |
| Unbounded thrash if the catalog check itself is buggy and always reports ready | Independent, small, hard-capped budget (3 attempts / 5 min / 01:00Z) — never removed even if the readiness signal is wrong. |
| Alert fatigue from a long stall | Two distinct once-per-day CRITICAL alerts, not per-poll; per-poll stays at `log_decision` (DEBUG-equivalent), matching existing conventions. |
| R7b's dead `disambiguate_exit_config_error`/`ExitConfigErrorCause` left stranded, confusing future readers | Call this out to the implementing agent: either delete it (with its two tests) as superseded, or explicitly document why it's retained un-wired — a design decision for the peer review, not silently left. |

## Does this change what the node trades?

No. Every change is confined to `trade_supervisor.py`/`trade_supervisor_core.py` (process-lifecycle scheduling) plus one new read-only helper in `composition.py`. No decision, sizing, exit, calibration, permit-validity, or A1-halt logic is touched — a boot-retry-spawned child passes through the identical self-check/permit/exit-rule/risk-cap gates any normal boot does. The only observable behavioral change is *whether/when a node process exists at all* on a day the catalog was transiently lagging; what it does once running is unchanged.
