## FU-8b plan: periodic timer re-poll of the runtime refusal watches

## Scope
**In:**
- A native Nautilus `LiveClock` timer re-polls the two runtime surfaces whose handlers today fire only on `ComponentStateChanged`:
  - `install_reconciliation_refusal_alert` (`src/breezy/runtime/component_health_watch.py:265-319`)
  - `install_stale_intent_alert` (`:154-230`)
- This is the hunter finding routed to FU-8b (`docs/plans/backlog/FU-8_resolver_cross_session_fill_plan_r2_2026-09-26.md:141,162`). As things stand, a runtime latch such as `resolver_fill_not_booked`, or an intent crossing the 15-minute staleness age (`client.py:569`), sits unalerted until some unrelated component changes state.
- The timer is armed in the composition root `_run_node` (`src/breezy/runtime/trade_cli.py:461-619`), where both handlers are already installed (`:576-583`).

**Out (explicitly):**
- `install_component_degraded_alert` (`:322-396`). Its signal *is* the DEGRADED `ComponentStateChanged`, so polling adds nothing.
- The `current_rung_hold` secondary path (`composition.py:876-893`). Its primary path is already per-tick (`:815-822`), it is wired in `app/trade.py` rather than `_run_node`, and extending it is YAGNI until a gap is shown.
- The residual "boot mass-status raises → generic `_refuse`" (`FU-8 plan :151`). That is a boot-path attribution gap, not a delivery gap, and no timer fixes it. It stays a named residual.
- No synthetic `ComponentStateChanged` is ever published (`FU-8 plan :141`: it would spoof a native event).
- No change to the exec client, the alert sink, `health.py`, any latch semantics, `allow_short`, operator caps or NO-SEND.

## L-1 null-hypothesis verdict
- **Native timer exists → reuse, do not build.** Installed nautilus 1.231.0 provides:
  - `Clock.set_timer(name, interval, start_time, stop_time, callback, allow_past, fire_immediately)` (`nautilus_trader/common/component.pyx:419-482`)
  - `LiveClock.set_timer_ns`, which refuses a duplicate name via `Condition.not_in(name, self.timer_names)` (`:930-941`)
  - `cancel_timer` / `cancel_timers` (`:543-565`)
  - `TestClock.advance_time`, which returns `TimeEventHandler`s (`:790-836`) that fire through `.handle()` (`:1165-1169`)
- **Native lifecycle exists → reuse.**
  - `NautilusKernel.stop` and `stop_async` both call `_cancel_timers()` on the kernel clock (`system/kernel.py:1059,1100`). `_cancel_timers` logs `Canceled Timer(name=…)` for each timer (`:1443-1446`).
  - `kernel.dispose()` does **not** cancel clock timers (`:1108-1135`). So the dispose path after a failed or aborted run needs an explicit cancel. That is the only thing built here.
- **Native periodic reconciliation is the wrong tool.** `open_check_interval_secs` / `position_check_interval_secs` (`live/config.py:188,195`) re-run venue reconciliation, which means venue I/O. They do not re-read Breezy's in-memory refusal surfaces. Enabling `position_check_interval_secs` is also prohibited by standing ruling (memory: execute-backlog 2026-09-12).
- **What genuinely does not exist:** a periodic trigger that joins the kernel clock to the two already-returned handler closures. That join, plus a thread hop, is the entire build.
- **Thread fact that shapes the design (measured and pinned):** a `LiveClock` callback runs on a Rust/tokio thread, not the asyncio loop thread (`tests/contract/test_live_timer_thread_affinity.py:7-12`). The pyo3 wrapper calls the callback directly (`component.pyx:1006-1010`).
- **L-16:** a raise in that callback is silently discarded (`docs/core/LESSONS.md:772-819`; `test_live_timer_thread_affinity.py`, the "swallowed_and_the_timer_keeps_firing" test).

## Acceptance Criteria
1. `_run_node` arms exactly one timer named `REFUSAL_REPOLL_TIMER_NAME` on `node.kernel.clock` after `node.build()` and after both handlers are installed, with interval `REFUSAL_REPOLL_INTERVAL` (60 s).
2. Each timer fire runs the reconciliation-refusal handler and then the stale-intent handler, both **on the kernel event-loop thread**, via `loop.call_soon_threadsafe`.
3. A reconciliation latch (including `RESOLVER_FILL_NOT_BOOKED`) added at runtime is alerted within ≤1 interval, with **no** `ComponentStateChanged` published.
4. An intent that enters `stale_ambiguous_intent_alerts` at runtime is alerted within ≤1 interval, with no state-change event.
5. Idempotence: for any interleaving of the timer trigger and the state-change trigger, each `(latch, subject)` and each `intent_id` alerts exactly once. The existing dedupe sets (`component_health_watch.py:196,287`) are shared because both triggers call the same closure.
6. The timer callback never raises, in any of these cases:
   - loop closed;
   - `call_soon_threadsafe` raising;
   - any `BaseException` from scheduling.

   Failures are logged at ERROR with exception **type only** (the `emit_alert` discipline, `health.py:681-699`).
7. A handler that raises inside the loop-thread poll is logged. It does not prevent the other handler from running in the same tick, and it does not stop later ticks.
8. The timer is cancelled on every exit of `_run_node`: normal return, `KeyboardInterrupt`, and `BaseException`. Cancellation happens before `node.dispose()` and is idempotent alongside the kernel's own `_cancel_timers`.
9. Arming failure is **non-fatal but loud**. The node boots, with ERROR plus a stderr line `refusal re-poll timer NOT armed`, and the state-change path is unchanged. Rationale: this is informational delivery, not a control (FU-8 r2.1 ruling), and it must never cost a trading day (L-48 spirit).
10. A successful arm writes one INFO line, `refusal re-poll timer armed name=… interval_s=60`, through the `breezy` logger. The bridge is installed at `trade_cli.py:663`, before `_run_node` at `:710` (L-30 positive signal).

## Edge Cases & NFRs
- **Armed before `node.run()`.**
  - The loop exists at that point: `TradingNode.__init__` obtains it (`live/node.py:65-79`), and `kernel.loop` returns `self._loop` (`kernel.py:654-663`).
  - `call_soon_threadsafe` on a not-yet-running loop queues the callback until `run_until_complete` (`node.py:298`).
  - This is verified by contract test 18 rather than assumed.
- **Fire during boot reconciliation.** The handler reads a partial latch set. This is safe:
  - the latch dict is replaced copy-on-write (`client.py:3545-3548`);
  - dedupe covers any later latches;
  - the post-reconciliation `ComponentStateChanged` still fires (`component_health_watch.py:275-278`).
- **Readers touch no store.** Both return tuples of in-memory dict values (`client.py:1602-1614, 2019-2041`), so the thread-confined `_require_store` (`:4019`) is never reached. The thread hop is still mandatory: it serialises mutation of the dedupe sets with the msgbus trigger.
- **Stale-intent forget semantics are unchanged.** An id dropped from the surface (retired) is forgotten, and a later id re-alerts (`:211-212`).
- **Timer firing after the loop is closed** (dispose path when cancel was skipped): the callback checks `loop.is_closed()` and returns silently. No 60-second ERROR spam.
- **NFR cost:** per minute, two tuple copies of ≤ a handful of entries and set lookups. No I/O, no allocation growth (L-29; the sets are bounded by the latches).
- **Portability:** the module still names no venue (`test_exec_refusal_health_surface.py:710-725` stays green). `asyncio` is the only new import.

## Design & Data Flow
**Flow:**
1. `_run_node` builds the node and installs both watches. The returned handler closures are now captured (today they are discarded at `:576-583`).
2. `install_refusal_repoll_timer(clock=node.kernel.clock, loop=node.kernel.loop, handlers=(recon_h, stale_h))` calls `clock.set_timer(REFUSAL_REPOLL_TIMER_NAME, REFUSAL_REPOLL_INTERVAL, callback=_on_timer)`.
3. On each fire, `_on_timer` runs on the tokio thread. Inside `try/except BaseException` it returns if the loop is closed, and otherwise calls `loop.call_soon_threadsafe(_poll, event)`.
4. `_poll` runs on the loop thread and calls each handler inside `try/except Exception` with `logger.exception`.
5. The function returns an idempotent `cancel()` that cancels the timer if its name is still in `clock.timer_names`, swallowing `KeyError`/`ValueError` at DEBUG.
6. `_run_node`'s `finally` calls `cancel()` before `node.dispose()`.

**Options considered:**
- **(A) Kernel-clock timer in the composition root. CHOSEN.**
  - It matches the ruled site (`FU-8 plan :141`).
  - Kernel stop cancels it natively (`kernel.py:1059,1100`).
  - It needs no Actor. The module's own rationale against an Actor still holds (`component_health_watch.py:29-35`), and `actors=[]` stays untouched.
- **(B) A dedicated Actor with `on_start` / `on_stop`, like `FeeDriftProbeActor` (`fee_drift_probe.py:248-277`).** Rejected:
  - the handlers are built after `build()`, but actors must register before it (`trade_cli.py:554-557`);
  - an actor clock has the same tokio-thread problem;
  - it adds a component, and a `ComponentStateChanged` source, for no gain.
- **(C) A synthetic `ComponentStateChanged` publish.** Rejected by ruling: it spoofs a native event.
- **(D) Calling handlers directly in the timer callback.** Rejected:
  - the handler would run off-loop and race the msgbus trigger on the dedupe sets;
  - an uncaught raise would vanish (L-16).

**Interval: `REFUSAL_REPOLL_INTERVAL: Final[timedelta] = timedelta(seconds=60)`.**
- The stale threshold is 15 minutes (`client.py:569`), so 60 s adds at most 6.7% latency.
- Surfaces change at most every resolver pass (5 s, `client.py:551`), so a sub-5-second poll is waste.
- Operator alert latency is meaningful at minute granularity.
- The cost is negligible.

**`fire_immediately=False`:** the first post-boot read is already guaranteed by the post-reconciliation `ComponentStateChanged` (`:275-278`).
