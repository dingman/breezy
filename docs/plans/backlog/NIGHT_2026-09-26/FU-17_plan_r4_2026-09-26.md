## Root cause (measured, not assumed)

1. `NoTradableInstrumentsError` (`composition.py:166-171`) is raised at `composition.py:522` via `_zero_instruments_message` (`composition.py:406-415`), producing the literal `"current_rung_hold: resolved 0 instruments for <date> (<counts>); refusing to start"`. `app/trade.py`'s broad exception handler prints this to stderr, and `spawn_node` redirects `stderr=subprocess.STDOUT` into the tailed node log — unconditional, independent of logging level.
2. `_do_relaunch_check` classifies via `classify_exit1_cause` (`trade_supervisor_core.py:518-531`): `PERMIT_NOT_ISSUED_MARKER`→DETERMINISTIC, `TRADING_NODE_FAILED_MARKER`/`FATAL_*`→TRANSIENT, else UNKNOWN. The zero-instrument text matches none of these today, so `decide_relaunch` declines with `"exit cause is not transient"`.
3. **Structural finding (the actual "whole day lost" cause):** `next_due`'s MIDDAY_WATCH branch (`trade_supervisor_core.py:1023-1028`) only fires when readiness was ever observed. Once RELAUNCH_CHECK's budget exhausts with readiness never observed, `next_due` returns `Phase.NONE` for the rest of the day.
4. **Stale-`tracked_pid` dead-end:** `_do_relaunch_check`'s decline path returns `tracked_pid=None` (`trade_supervisor.py:1205`), but `_do_midday_watch`'s own decline paths deliberately return the **same, still-dead `tracked_pid`**, never `None`. The correct, persistent "still in boot-retry territory" signal is `state.first_boot_permit_expires_at_ns is None` (a day-level anchor untouched by dead-child bookkeeping), not `tracked_pid`.
5. **[r2→r3, architect item 1] `classify_exit1_cause`'s `TRANSIENT` bucket is NOT specific to the zero-instrument refusal.** `TRADING_NODE_FAILED_MARKER`/`FATAL_*` are emitted by a node that can have already minted a permit and traded before failing later in the day. **Fix (unchanged from r3):** a narrower, dedicated day-level latch, `boot_zero_instruments_seen`, set ONLY by a direct `zero_instruments_refusal_in(log_text)` check — never inherited from `classify_exit1_cause`'s broader bucket.
6. **[r2→r3, python item 7; r3→r4 item B, arithmetic corrected] r2's AC7 (`BOOT_RETRY_WINDOW_CLOSED_NEVER_READY`) was claimed unreachable by an arithmetic error.** `next_due` only ever returns `Phase.MIDDAY_WATCH` while `now < watch_close_at` (01:00Z the next day), and `decide_boot_retry` consumes an attempt on **every** eligible poll. With `BOOT_RETRY_MIN_GAP`=15min and `BOOT_RETRY_MAX_ATTEMPTS`=8, and assuming each retry child dies effectively instantly (the fast-dying-children case), the budget is consumed on a deterministic, unbroken 15-minute cadence starting at `SELF_CHECK_WINDOW_END_UTC`=17:10Z (`watch_open_at`). **Corrected arithmetic:** attempt 1 is due at 17:10Z (no prior attempt, no gap to wait on); each subsequent attempt is due exactly `BOOT_RETRY_MIN_GAP` after the previous, so attempt *k* (1-indexed) is due at `17:10Z + (k-1)×15min`. The 8th attempt is therefore due at `17:10Z + 7×15min = 17:10Z + 105min = **18:55Z**` — **not** r3's `19:55Z** (a plain arithmetic slip: 7×15=105min=1h45min, and 17:10+1:45=18:55, not 19:55). This is roughly **six hours**, not "roughly five," before `midday_watch_window_end`=01:00Z. **[r3→r4, item C] This corrected arithmetic only holds under the fast-dying-children assumption used to derive it.** Item C (below) shows the assumption is false in general: `decide_boot_retry`'s step (b) only runs once a spawned child is confirmed dead, so a child that stays alive for e.g. 3 hours before dying transiently stretches the whole 8-attempt sequence past 01:00Z with the budget never exhausting and no terminal alert firing. **Fix, revised from r3:** keep `decide_boot_retry` itself free of any `window_end`/`cause`/`catalog_ready` parameter (unchanged from r2→r3, decision still correct — a pure per-call budget/gap check has no business knowing about wall-clock window state), but reinstate a window-close alert as a SEPARATE, unconditional per-tick check (`boot_retry_window_closed`/`_do_boot_retry_window_closed_check`) rather than as a branch inside `decide_boot_retry` or `_do_boot_retry` — this is what actually differs from r2's design, not merely a constants fix.
7. Ingest cadence is `OnCalendar=*:0/15` (`deploy/systemd/breezy-quote-tape-ingest-frequent.timer:21`). The boot-time schedule itself budgets 15 minutes (`LAUNCH_UTC`=16:50 → `SELF_CHECK_UTC`=17:05) for a healthy boot to prove readiness — the basis for `BOOT_RETRY_MIN_GAP` (unchanged).
8. `disambiguate_exit_config_error`/`ExitConfigErrorCause` is dead code — its only callers are its own two unit tests. Per decision I: **delete**, not re-wire (unchanged).
9. **[r3→r4, architect item A, new] Adoption (or an unresolved log path) hides a pre-existing permit from the supervisor, which the r3 entry guard misreads as "still safe to spawn unclamped."** r3's `_do_boot_retry` entry guard treats `state.first_boot_permit_expires_at_ns is None` as sufficient proof that no permit exists yet today. But that field is only ever set by actually READING a permit-issued log line (`record_first_boot_permit_seen`, called from `_do_relaunch_check`/`_do_midday_watch`/the new `_do_boot_retry` itself). Three existing call sites can attach `tracked_pid` to an already-live process WITHOUT ever reading (or being able to read) that process's log history: `_do_launch`'s own adoption path, B1's `_permit_watch_adopt_and_evaluate` (per-iteration adoption, `trade_supervisor.py:1403-1409`), and `_do_self_check`'s adoption path (`trade_supervisor.py:1627-1633`) — plus, once this plan adds it, `_do_boot_retry`'s own reuse of the same `decide_launch_action`/`_attempt_adoption` precheck. Concrete failing interleaving: (a) a live, lock-holding node is adopted with `node_log=None` (log path undiscoverable, e.g. an operator hand-relaunch per the `hand-relaunch-mechanics` lesson); this node may already hold a permit; (b) `boot_zero_instruments_seen` stays `True` and `first_boot_permit_expires_at_ns` stays `None` (nothing was ever read to set it); (c) the node dies, the lock frees; (d) r3's entry guard is still satisfied (`boot_zero_instruments_seen and not readiness_observed and first_boot_permit_expires_at_ns is None and neither terminal alert sent`), so `_do_boot_retry` dispatches and mints a SECOND, unclamped permit while the first may still be live/expiring independently. **Fix:** see AC16.

## Hard-invariant cross-check (permit clamp)

**[r3→r4, re-derived per architect item A to include the adoption/unknown-log interleaving.]** The operating brief's standing invariant — *the A-1 permit-expiry clamp must hold in EVERY interleaving; no boot-retry spawn may occur whenever a permit might exist that the supervisor has not observed* — is satisfied by AC10/AC11/AC16 together, not by AC10/AC11 alone as r3 claimed:

- **Without AC16 (r3's gap):** r3's entry guard used `first_boot_permit_expires_at_ns is None` as the sole "no permit exists yet" proof. That field is only set by READING a permit line. An adoption with an unknown/undiscoverable log path (or, more subtly, a known log path attached only after the permit line already scrolled past) can leave `first_boot_permit_expires_at_ns` at `None` while a permit genuinely already exists on the adopted node — a state where "the supervisor has not observed" a permit that "might exist" is exactly true, and the invariant's own wording forbids a boot-retry spawn in that state. r3's guard did not forbid it: it dispatched `_do_boot_retry` anyway (root cause item 9's failing interleaving).
- **With AC16:** the moment ANY adoption occurs, or a tracked child's log path is ever unknown, `boot_retry_adoption_seen` (or the direct `node_log is None` check) permanently disqualifies `_do_boot_retry` for the rest of the day. Control falls to `_do_midday_watch`'s unmodified body, which independently enforces the SAME "unobserved permit ⇒ no spawn at all" rule via its existing `first_boot_permit_expires_at_ns is None` → `CEILING_UNKNOWN` branch (`trade_supervisor.py:1312-1338`, pre-dating this plan, A-1's own 2026-09-25 fix) — a branch that refuses to spawn *anything*, clamped or unclamped, rather than merely clamping. So the adopted-node case degrades to "no relaunch at all until a permit IS observed," never to "spawn anyway."
- **Combining with the un-amended part of the proof (unchanged from r3):** AC10/AC11 together mean `_do_boot_retry`'s own, non-adoption spawns can structurally only ever occur **before** any permit exists today (`first_boot_permit_expires_at_ns is None` AND no adoption/unknown-log event has occurred to hide one) — the exact situation `_do_relaunch_check`'s own pre-existing, unclamped `env=os.environ` boot-time relaunch is already in, unchanged code. The instant a permit IS observed (AC11, now including the hand-off readiness-latch fix for item H), routing permanently leaves `_do_boot_retry` and falls under the existing, already-clamped mid-day-relaunch path for the rest of the day.
- **Net:** at every point in time, exactly one of three things is true: (1) no permit exists yet and no adoption/unknown-log event has occurred — boot-retry may spawn unclamped, and there is nothing yet to violate; (2) a permit was actually observed — every subsequent relaunch is clamped, per existing A-1 code; or (3) an adoption/unknown-log event occurred and no permit has been observed — `_do_boot_retry` is permanently disqualified and `_do_midday_watch`'s CEILING_UNKNOWN branch refuses every spawn outright until a permit IS observed. No interleaving reaches a state with both an unclamped spawn option available AND an unobserved, possibly-already-minted permit to protect.

## Edge Cases & NFRs

- **Duplicate-boot / adopted-live-node race:** unchanged — reuses `decide_launch_action`/`_attempt_adoption`.
- **Stale dead-pid dead-end (root cause item 4):** unchanged from r3.
- **Permanent zero-instrument day:** unchanged from r3 (fails closed via attempt-budget exhaustion — AC8 — now backstopped by the window-closed alert for the slow-dying-children sub-case).
- **Precheck-refusal thrash (decision F):** unchanged from r3.
- **Non-transient child re-exit (decision D):** unchanged from r3.
- **A never-ready retry child that never dies:** unchanged from r3 (AC8's `BOOT_RETRY_CHILD_NOT_READY`), now with the anchor-fallback fix (AC18/item F) so the boot-time-carried-over child is covered too.
- **[r3→r4, item C, new] A retry child that dies only after a long, live interval, repeatedly, never exhausting the 8-attempt budget by day close:** closed by the reinstated `BOOT_RETRY_WINDOW_CLOSED_NEVER_READY`, fired once by the new unconditional per-tick check regardless of how few attempts were consumed.
- **[r3→r4, item A, new residual — accepted, not solved] An adopted node with an unknown log path that never dies and whose log path is never later resolved, during a boot-zero-instruments day:** `boot_retry_adoption_seen` correctly prevents an unclamped double-spawn (the hard invariant this plan protects), but neither `CEILING_UNKNOWN` (requires observing the node dead) nor the new window-closed check (deliberately excludes `boot_retry_adoption_seen` days, since CEILING_UNKNOWN is that branch's own terminal signal once the node does die) fires in this specific sub-case. This is an accepted, explicitly named residual observability gap — the safety invariant holds (no bad spawn), but the operator may get no terminal alert for that day. Out of scope for this plan (item A's ask was to close the spawn-safety gap, not to design a new alert surface for an already-adopted node); flagged as a follow-up.
- **Supervisor restart mid-retry-window (decision H, non-goal):** unchanged from r3; the two new day-level latches (`boot_retry_adoption_seen`, `boot_retry_window_closed_alert_sent`) reset to `False` on restart exactly like every other field, same accepted limitation.
- **A1 halt / operator caps:** orthogonal, untouched.

## Design & Data Flow — options considered

Unchanged from r3: (a) marker→TRANSIENT-only-inside-RELAUNCH_CHECK insufficient; (b) catalog-readiness gate rejected (layering violation); (c) ingest-completion event rejected (no native hook, YAGNI). **Recommended (unchanged shape, r3→r4 structurally adds one new always-on per-tick check and one new day-level latch, both additive to the existing cause-gated + fixed-cadence-and-budget-gated retry):** `decide_boot_retry` stays a pure, wall-clock-window-unaware attempt/gap check (no new parameter); the window-close case is handled entirely OUTSIDE it, by a separate, unconditional per-tick predicate — this needs no new port, no new I/O surface, and no layering change.
