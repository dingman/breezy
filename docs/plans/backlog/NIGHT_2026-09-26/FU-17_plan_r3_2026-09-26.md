## L-1 null-hypothesis verdict

Confirmed against installed capability: Nautilus itself offers no relaunch/retry/scheduling primitive — that machinery (`Phase`, `next_due`, `DaySchedulerState`, `decide_relaunch`) is Breezy's own extension in `src/breezy/runtime/trade_supervisor_core.py`, so the gap is closed by extending that existing extension point. This design reads no Nautilus/Parquet catalog from the supervisor at all (unchanged from r2 — see decision A): a runtime-owned port reading `strategy/current_rung_hold/composition.py` would be a `runtime → strategy` import, forbidden by `pyproject.toml:69-97`'s exhaustive layers contract (`runtime` below `strategy`, "Runtime never imports strategy"). The one catalog-adjacent code touched remains the marker **text**: its constants live in `runtime` (the lower layer, stdlib-only — item 5), and `composition.py` imports them **downward**, the direction the layering rule already permits.

## Root cause (measured, not assumed)

1. `NoTradableInstrumentsError` (`composition.py:166-171`) is raised at `composition.py:522` via `_zero_instruments_message` (`composition.py:406-415`), producing the literal `"current_rung_hold: resolved 0 instruments for <date> (<counts>); refusing to start"`, all on one log line. `app/trade.py`'s broad exception handler and `_report(...)` print this to stderr, and `spawn_node` redirects `stderr=subprocess.STDOUT` into the tailed node log — unconditional, independent of logging level.
2. `_do_relaunch_check` classifies via `classify_exit1_cause` (`trade_supervisor_core.py:518-531`): `PERMIT_NOT_ISSUED_MARKER`→DETERMINISTIC, `TRADING_NODE_FAILED_MARKER`/`FATAL_*`→TRANSIENT, else UNKNOWN. The zero-instrument text matches none of these today, so `decide_relaunch` (`trade_supervisor_core.py:549-570`) declines with `"exit cause is not transient"`.
3. **Structural finding (the actual "whole day lost" cause):** `next_due`'s MIDDAY_WATCH branch (`trade_supervisor_core.py:1023-1028`, confirmed verbatim: `if effective.launch_done and effective.readiness_observed and watch_open_at <= now_utc < watch_close_at`) only fires when readiness was ever observed. Once RELAUNCH_CHECK's budget exhausts with readiness never observed, `next_due` returns `Phase.NONE` for the rest of the day.
4. **Stale-`tracked_pid` dead-end:** `_do_relaunch_check`'s decline path returns `tracked_pid=None` (`trade_supervisor.py:1205`), but `_do_midday_watch`'s own decline paths deliberately return the **same, still-dead `tracked_pid`**, never `None` (`trade_supervisor.py:1257-1260,1308,1338,1359`, docstring lines 1250-1256 state this explicitly). A boot-retry entry guard written as `tracked_pid is None` would therefore fire exactly ONCE. The correct, persistent "still in boot-retry territory" signal is **`state.first_boot_permit_expires_at_ns is None`** (a day-level anchor untouched by dead-child bookkeeping), not `tracked_pid` — confirmed still true against the current `_do_midday_watch` body (verbatim, lines 1214-1373).
5. **[r2→r3, architect item 1] `classify_exit1_cause`'s `TRANSIENT` bucket is NOT specific to the zero-instrument refusal.** Verbatim (`trade_supervisor_core.py:518-531`):
   ```python
   def classify_exit1_cause(log_text: str) -> RelaunchCause:
       if PERMIT_NOT_ISSUED_MARKER in log_text:
           return RelaunchCause.DETERMINISTIC
       if TRADING_NODE_FAILED_MARKER in log_text:
           return RelaunchCause.TRANSIENT
       if FATAL_MARKET_DATA_FAULT_MARKER in log_text or FATAL_EXEC_CLIENT_FAULT_MARKER in log_text:
           return RelaunchCause.TRANSIENT
       return RelaunchCause.UNKNOWN
   ```
   `TRADING_NODE_FAILED_MARKER` and the two `FATAL_*` markers are emitted by a node that can have **already minted a permit and traded** before failing later in the day (e.g. a mid-day market-data fault). A boot-retry entry guard keyed on `boot_cause_seen is RelaunchCause.TRANSIENT` (r2's design) would therefore be satisfiable by a completely unrelated, later-in-the-day failure mode that has nothing to do with an empty catalog — a real false-positive path into `_do_boot_retry`, not a style nit. r2's own `first_boot_permit_expires_at_ns is None` outer condition happens to close most of this gap in practice (a node that minted a permit already has that field set), but relying on that interaction implicitly, rather than naming the correct latch explicitly, is exactly the kind of coincidental correctness this review flags. **Fix:** a narrower, dedicated day-level latch, `boot_zero_instruments_seen`, set ONLY by a direct `zero_instruments_refusal_in(log_text)` check — never inherited from `classify_exit1_cause`'s broader bucket.
6. **[r2→r3, python item 7] r2's AC7 (`BOOT_RETRY_WINDOW_CLOSED_NEVER_READY`) is unreachable.** `next_due` only ever returns `Phase.MIDDAY_WATCH` while `now < watch_close_at` (`midday_watch_window_end`, 01:00Z the next day), and `decide_boot_retry` consumes an attempt on **every** eligible poll (decision F — unconditionally, before the precheck). With a fixed `BOOT_RETRY_MIN_GAP` and `BOOT_RETRY_MAX_ATTEMPTS`, the budget is therefore consumed on a deterministic, unbroken 15-minute cadence starting no earlier than `SELF_CHECK_WINDOW_END_UTC` = 17:10Z (the earliest instant `_do_midday_watch` can dispatch at all, per `next_due`'s own `watch_open_at`). At `BOOT_RETRY_MAX_ATTEMPTS=8`, the 8th attempt fires at 17:10Z + 7×15min = **19:55Z**, and the exhaustion alert fires on the next eligible poll after that (~20:10Z) — roughly **five hours** before `midday_watch_window_end` (01:00Z). The window-close branch can never be reached by any value of `now` the retry loop will ever observe, for any attempt count that keeps the arithmetic below ~33 attempts (8 is far under that). **Fix, per the review's own recommendation:** drop the window-end parameter/branch from `decide_boot_retry` entirely; keep `BOOT_RETRY_ATTEMPTS_EXHAUSTED` as the sole terminal budget alert; pin the arithmetic with a dedicated test so a future constant change that reopens this gap fails loudly instead of silently.
7. Ingest cadence is `OnCalendar=*:0/15` (`deploy/systemd/breezy-quote-tape-ingest-frequent.timer:21`). The boot-time schedule itself budgets 15 minutes (`LAUNCH_UTC`=16:50 → `SELF_CHECK_UTC`=17:05, `trade_supervisor_core.py:34-35`) for a healthy boot to prove readiness — the basis for `BOOT_RETRY_MIN_GAP` (unchanged from r2).
8. `disambiguate_exit_config_error`/`ExitConfigErrorCause` (`trade_supervisor_core.py:317-321,534-540`) is dead code — its only callers are its own two unit tests. Per decision I: **delete**, not re-wire (unchanged from r2).

## Acceptance Criteria

1. A boot whose log carries the exact zero-instrument **refusal** marker — `ZERO_INSTRUMENTS_REFUSAL_PREFIX` followed, **on the same line**, by `ZERO_INSTRUMENTS_REFUSAL_SUFFIX` (enforced by a per-line regex, not a whole-text substring check — item 4) — is classified `RelaunchCause.TRANSIENT` by `classify_exit1_cause`. Three regression tests, texts verified live against the repo:
   - `settings.py:303`'s `"...there is nothing to run; refusing to start with an empty site set"` contains the literal suffix fragment `"; refusing to start"` but **never** the prefix — must not match.
   - `composition.py`'s skip warning, `"current_rung_hold: skipping %s; resolved 0 instruments for %s"` (lines 528-532), and its yesterday warning, `"%s resolved 0 instruments for yesterday %s; external order claim covers today only"` (lines 693-698), each contain a "resolved 0 instruments for" fragment but **never** the full, contiguous `ZERO_INSTRUMENTS_REFUSAL_PREFIX` (the station name/`"skipping %s; "` text sits between `"current_rung_hold:"` and `"resolved"`), and neither carries the suffix — must not match either constituent test.
2. **[r2→r3, architect item 1, new]** A dedicated day-level latch `boot_zero_instruments_seen` is set **only** by a direct `zero_instruments_refusal_in(log_text)` check on every log read (the original boot's `_do_relaunch_check` read, and every later boot-retry child's own read) — **never** inferred from `classify_exit1_cause(...) is RelaunchCause.TRANSIENT`, which also covers `TRADING_NODE_FAILED_MARKER`/`FATAL_*` and can fire on a child that already minted a permit and traded. Regression tests pin that seeing `TRADING_NODE_FAILED_MARKER` or either `FATAL_*` marker alone does **not** set `boot_zero_instruments_seen`.
3. With `readiness_observed=False` at 17:00Z and `boot_zero_instruments_seen` latched `True`, `next_due` returns `Phase.MIDDAY_WATCH` from 17:10Z onward (not `Phase.NONE`).
4. With `boot_zero_instruments_seen` still `False` — including the case where a *different* `TRANSIENT` cause (e.g. `TRADING_NODE_FAILED_MARKER`) was seen during boot but the zero-instrument marker never was — `next_due` still returns `Phase.NONE` once the boot-time budget exhausts. New regression test for this exact "TRANSIENT-but-not-zero-instruments" case (the scenario item 1 exists to close).
5. There is **no catalog read anywhere in the retry path** (decision A, unchanged). A boot-retry attempt is always spent when `decide_boot_retry` says eligible; a permanently-empty catalog therefore exhausts the fixed 8-attempt/15-minute-gap budget (~3 hours after 17:10Z) and fires `BOOT_RETRY_ATTEMPTS_EXHAUSTED` CRITICAL — an explicitly accepted trade-off, not a defect.
6. Every spawn in the boot-retry path is gated by the same lock/PID/adoption precheck `_do_launch` already performs (`decide_launch_action`, `_attempt_adoption`) — never a bare `ports.spawn` (unchanged from r2).
7. **[r2→r3, architect item 6, rewritten]** Boot-retry's budget is its own counter, independent of `relaunch_attempts`/`midday_relaunch_attempts`: **≤8 attempts, ≥15 minutes apart**. There is no window-end check (see AC8/root-cause item 6 for why). The very FIRST eligible attempt of the day additionally fires `BOOT_RETRY_FIRST_ATTEMPT` WARN once, so the operator is notified the moment the system enters boot-retry territory at all — distinct from, and always preceding, the terminal CRITICAL alerts.
8. **[r2→r3, python item 7 + architect item 3, rewritten — corrects r1's/r2's false AC8]** There are exactly two terminal, once-per-day CRITICAL alerts for the boot-retry path: `BOOT_RETRY_ATTEMPTS_EXHAUSTED` (budget consumed) and `BOOT_RETRY_CHILD_NONTRANSIENT_EXIT` (a retry child died with a non-`TRANSIENT` cause; permanently stops the path — AC13). There is **no** `BOOT_RETRY_WINDOW_CLOSED_NEVER_READY` alert: dropped, because the fixed 8×15-minute budget always exhausts hours before `midday_watch_window_end` (root cause item 6; pinned by `test_boot_retry_budget_exhausts_hours_before_midday_watch_window_close`). Each precheck refusal (`REFUSE_LOCK_HELD`/`REFUSE_INTENT_OPEN`) alerts its own distinct `AlertDetail`, unlatched per-occurrence, exactly as `_do_launch`'s own precedent (unchanged from r2 — AC14). **New:** a boot-retry child that stays alive without ever producing a permit-issued line for longer than `BOOT_RETRY_READINESS_TIMEOUT` (15 minutes, anchored at `last_boot_retry_attempt_at`) alerts `BOOT_RETRY_CHILD_NOT_READY` WARN once per retry child (latched via a new per-child field, cleared for the next retry child by `record_child_adopted`) — observability only, never a forced extra attempt. This closes the gap the python/architect review found in r1's/r2's AC8, which falsely implied readiness-tracking machinery that was never actually wired for a boot-retry child.
9. **[r2→r3, architect item 2, rewritten]** A boot-retry child's own exit cause is decided from the **latched** `state.midday_cause_seen` value — the exact same drain-safe, first-seen-wins field `_do_midday_watch` already relies on for its own child, latched via `record_midday_cause_seen` on **every** poll of the retry child (alive or dead), never from a fresh, possibly-already-drained `classify_exit1_cause(log_text)` read at the moment death is detected. A boot-retry child's readiness prior to permit-issuance is otherwise not tracked by `readiness_observed()`/`midday_readiness_recheck_done` — that machinery is reserved for a child that already has an anchored first-boot permit (reachable only via `_do_midday_watch`'s ordinary body, after AC11's hand-off) — and liveness-without-permit is bounded solely by AC8's new not-ready timeout. Pinned by a test: the transient marker line is observed on one poll while the child is still alive (latching `midday_cause_seen`), and the process is confirmed dead on a *later* poll whose log delta no longer contains the line — the decision must still come from the latch, not reclassify a now-empty delta as `UNKNOWN` and wrongly treat it as a non-transient stop.
10. A boot-retry child mints its own, unrestricted first-boot permit exactly like a normal 16:50Z LAUNCH (`env=os.environ`, no `PERMIT_EXPIRY_CEILING_NS_ENV_VAR`) — never clamped, since no earlier boot succeeded today (unchanged from r2; see **Hard-invariant cross-check** below for why this satisfies, not violates, the A-1 permit-clamp invariant).
11. Once a boot-retry child's permit-issued line is observed, `record_first_boot_permit_seen` latches `first_boot_permit_expires_at_ns`, and from that poll onward **every** subsequent poll routes to the pre-existing mid-day-relaunch path — never back into the boot-retry branch. A later relaunch of this now-anchored child is capped by A-1/`decide_midday_relaunch`'s own existing budget exactly as any ordinary mid-day-relaunched child is, pinned by a test (unchanged from r2).
12. No file under `strategy/current_rung_hold/{decision,exit_decider,exit_authorization,tick_eval}.py`, `runtime/order_enablement.py`, or the A1 halt read path changes (unchanged from r2).
13. New `AlertDetail`/state fields are pure additions — six new `AlertDetail` members in r3 (`BOOT_RETRY_ATTEMPTS_EXHAUSTED`, `BOOT_RETRY_CHILD_NONTRANSIENT_EXIT`, `BOOT_RETRY_PRECHECK_REFUSED_LOCK_HELD`, `BOOT_RETRY_PRECHECK_REFUSED_INTENT_OPEN`, `BOOT_RETRY_FIRST_ATTEMPT`, `BOOT_RETRY_CHILD_NOT_READY` — net +1 vs r2's five, since `BOOT_RETRY_WINDOW_CLOSED_NEVER_READY` is dropped). There is **no** existing exact-set pin over `AlertDetail`/`RelaunchCause` to widen — only `CheckAlertDetail` is pinned (`tests/unit/test_alert_egress.py:29,218-219`), untouched by this plan (decision K, unchanged).
14. A retry child that boots and reaches readiness is still gated by the operator A1 halt exactly like any other node; a `boot_retrying`/`boot_retry_*` log or alert line must never be read as "trading resumed" (decision J, unchanged).
15. `lint-imports` (run with `PYTHONPATH=<worktree>/src`, per the worktree lesson) passes after every change: `composition.py`'s import of the two marker constants from `breezy.runtime.trade_supervisor_core` is a `strategy → runtime` "reach down," the direction the layers contract already permits; no file under `runtime/` gains an import of `strategy`/`composition.py` (decision K, unchanged).

## Hard-invariant cross-check (permit clamp)

The operating brief's standing invariant — *"the A-1 permit-expiry clamp on relaunches must stay intact: a retry must never spawn a child that could mint an unclamped permit"* — is satisfied, not contradicted, by AC10/AC11 together: A-1's clamp exists to stop a relaunch **after a permit already exists today** from minting a second, independently-expiring permit (the exact defect A-1 closed on 2026-09-25, `trade_supervisor.py:1312-1320,1365-1371`). Boot-retry's entry guard (AC2/AC3, `first_boot_permit_expires_at_ns is None`) means `_do_boot_retry` structurally can only ever spawn **before** any permit exists today — there is nothing yet to clamp against, exactly the same situation `_do_relaunch_check`'s own pre-existing, unclamped `env=os.environ` boot-time relaunch (`trade_supervisor.py:1209`, unchanged code) is already in. The instant a permit **is** observed (AC11), routing permanently leaves `_do_boot_retry` and falls under the existing, already-clamped mid-day-relaunch path (`trade_supervisor.py:1369-1371`) for the rest of the day. So at every point in time, exactly one of two things is true: no permit exists yet (boot-retry may spawn unclamped, and there is nothing to violate), or a permit exists (every subsequent relaunch is clamped, per existing A-1 code, untouched by this plan). No state exists where a retry both has an unclamped option available AND a prior permit to protect.

## Edge Cases & NFRs

- **Duplicate-boot / adopted-live-node race:** the retry branch reuses `decide_launch_action`/`_attempt_adoption`, never `ports.spawn` directly — identical protection to `_do_launch`'s own (unchanged).
- **Stale dead-pid dead-end (root cause item 4):** the retry branch's entry guard is keyed on `state.boot_zero_instruments_seen and not state.readiness_observed and state.first_boot_permit_expires_at_ns is None and not state.boot_retry_nontransient_alert_sent and not state.boot_retry_exhausted_alert_sent` — **not** `tracked_pid is None` — so a second, third, ..., eighth dead retry child (whose `tracked_pid` `_do_midday_watch`'s own convention keeps non-`None`, except on the terminal non-transient-exit stop, which does return `None`) still routes correctly. "No live child" is checked internally (log read + `ports.process_alive`) as the first thing `_do_boot_retry` does, not as an external routing precondition.
- **Permanent zero-instrument day:** no catalog check exists in this design (decision A); the day fails closed via ordinary attempt-budget exhaustion (~3 hours after 17:10Z) rather than a separate "catalog never ready" signal — an explicit, accepted simplification.
- **Precheck-refusal thrash (decision F):** an attempt is consumed (`record_boot_retry_attempt` called) **whenever `decide_boot_retry` says eligible**, regardless of whether the subsequent precheck ultimately spawns, adopts, or refuses — so a persistent `REFUSE_LOCK_HELD`/`REFUSE_INTENT_OPEN` condition is re-probed only once per 15-minute slot.
- **Non-transient child re-exit (decision D):** once a retry child's own latched cause (AC9) comes back non-TRANSIENT, the retry path alerts once (`BOOT_RETRY_CHILD_NONTRANSIENT_EXIT`) and permanently stops for the day.
- **A never-ready retry child that never dies (r2→r3, new — architect item 3):** without a timeout, a retry child that stays alive but never produces a permit-issued line would be watched silently for the rest of the day (no death → no re-classification, no permit → no hand-off, no alert). AC8's new `BOOT_RETRY_CHILD_NOT_READY` WARN closes this observability gap; it never forces an extra attempt or a kill.
- **Supervisor restart mid-retry-window (decision H, non-goal):** `DaySchedulerState` is in-memory, rebuilt on restart — a restart after 17:10Z resets `boot_zero_instruments_seen`/`boot_retry_attempts` to their initial values, and an in-progress retry sequence is simply forgotten. Pinned by a test, not solved — the same accepted limitation `relaunch_attempts`/`midday_relaunch_attempts` already carry today.
- **A1 halt / operator caps:** orthogonal, untouched; see AC14/decision J.

## Design & Data Flow — options considered

- **(a) Marker→TRANSIENT only, retried inside the existing RELAUNCH_CHECK budget.** Insufficient alone (unchanged from r1/r2): bounded to a ≤10-minute window that closes before most observed lags heal, and does nothing about `next_due`'s structural gate.
- **(b) Gate relaunch on catalog readiness (r1's recommendation).** Rejected outright (unchanged from r2): a `runtime → strategy` import forbidden by the layers contract; also carried r1's own MEDIUM-confidence station/day-manifest resolution gap.
- **(c) Ingest-completion event triggers a relaunch.** Rejected (unchanged): no native hook, new coupling/failure mode, violates YAGNI.
- **Recommended (unchanged shape from r2, tightened per r2→r3): cause-gated + fixed-cadence-and-budget-gated retry, inside the existing MIDDAY_WATCH window, no catalog read — but gated on a DEDICATED `boot_zero_instruments_seen` latch, not the general `classify_exit1_cause` `TRANSIENT` bucket.** `decide_boot_retry` uses its own fixed 15-minute/8-attempt budget with no `cause`/`catalog_ready`/`window_end` parameter at all (the cause gate lives entirely in the entry guard now, and the window-end check is dropped per item 7's arithmetic). This needs no new port, no new I/O surface, and no layering change.

## Risk Register

| Risk | Mitigation |
|---|---|
| Boot-retry double-spawns alongside an adopted live node | Reuse `decide_launch_action`/`_attempt_adoption` verbatim (AC6). |
| Stale dead-`tracked_pid` masks a live retry-eligible state (root cause item 4) | Entry guard keyed on `boot_zero_instruments_seen`+`first_boot_permit_expires_at_ns`+the two terminal-alert latches, never `tracked_pid` (decision C). |
| **[r2→r3]** A later, unrelated `TRANSIENT` failure (e.g. mid-day market-data fault on an already-trading node) is misread as "still a zero-instrument boot day" | Dedicated `boot_zero_instruments_seen` latch, set only by `zero_instruments_refusal_in`, never by the general `classify_exit1_cause` bucket (item 1, AC2/AC4). |
| **[r2→r3]** A prefix on one log line and an unrelated `"; refusing to start"` suffix on a different line coincide across a multi-line log delta, producing a false classification | Per-line regex (`zero_instruments_refusal_in`), not a whole-text substring check (item 4, AC1). |
| **[r2→r3]** A boot-retry child that stays alive but never mints a permit is silently watched forever with no signal | `BOOT_RETRY_CHILD_NOT_READY` WARN, once per child, timeout-anchored (item 3, AC8/AC9). |
| **[r2→r3]** A dead-code alert branch (`BOOT_RETRY_WINDOW_CLOSED_NEVER_READY`) that can never fire ships anyway, adding untestable-in-practice complexity | Dropped entirely from `decide_boot_retry`/`AlertDetail`; the underlying invariant is pinned by an arithmetic test instead so a future constant change surfaces the gap rather than reintroducing dead code silently (item 7, AC8). |
| Marker text drifts if `_zero_instruments_message` is edited later | Single source of truth in `runtime`; `composition.py` imports it downward (decision A/B, unchanged). |
| A runtime→strategy import creeps back in during implementation | `lint-imports` is a named gate item (AC15); no port/helper reads `composition.py` from `trade_supervisor.py`. |
| Boot-retry masks a real config error by retrying too broadly | Gated on the exact refusal marker only (AC1/AC2), AND on per-child re-classification stopping at the first non-TRANSIENT exit (decision D). |
| Precheck-refusal poll-cadence thrash | Attempt consumed on every eligible `decide_boot_retry` call regardless of precheck outcome — bounds re-probing to the 15-minute gap (decision F). |
| Unbounded thrash if the retry mechanism itself is buggy | Independent, small, hard-capped budget (8 attempts / 15 min), exhausting hours before day close with no readiness or catalog signal to short-circuit it. |
| Alert fatigue | Exhaustion/first-attempt/non-transient-exit/not-ready alerts fire at most once/day (or once/child) each; precheck-refusal alerts are per-occurrence but bounded to ≤8/day by the attempt budget itself. |
| A retry spawns an unclamped permit that collides with A-1's intent | See **Hard-invariant cross-check** — structurally impossible: boot-retry only ever runs before any permit exists today (AC10/AC11). |
| R7b's dead `disambiguate_exit_config_error`/`ExitConfigErrorCause` | Deleted with its two tests, explicitly as superseded dead code (decision I). |
| "Retry succeeded" alert read as "trading resumed" | AC14 states explicitly this design adds no A1-halt bypass. |
