## Scope

**In scope (design + plan only — no code, no venue calls, no live/systemd touch):**
- Why the four observed FU-17 zero-instrument refusals each cost a *whole* trading day, not just the 16:50–17:00Z window.
- How `_do_relaunch_check`/`_do_midday_watch`/`next_due` classify and gate a relaunch today, and the exact wiring gap that causes the loss.
- A recommended, bounded, **fixed-cadence** boot-retry design (no catalog-readiness port — see Changes from r1), its ACs, file-by-file plan, RED tests, and risk register.

**Explicitly out:** implementation, the A1 halt (stays operator-only, untouched by this design), `allow_short`, operator caps, permit-issuance semantics beyond the one new call site reusing existing issuance, and any change to what the node evaluates/decides once running.

## L-1 null-hypothesis verdict

Confirmed against installed capability: Nautilus itself offers no relaunch/retry/scheduling primitive — that machinery (`Phase`, `next_due`, `DaySchedulerState`, `decide_relaunch`) is Breezy's own extension in `src/breezy/runtime/trade_supervisor_core.py`, so the gap is closed by extending that existing extension point. **Revised from r1:** this design no longer reads the Nautilus/Parquet catalog from the supervisor at all. r1 proposed a `SupervisorPorts.catalog_day_ready()` port wrapping `composition.py`'s `_read_catalog_instruments`/`_bucket_station_instrument_ids` (`composition.py:317-339`) — but those live in `strategy/current_rung_hold/`, and `pyproject.toml:69-97`'s `[[tool.importlinter.contracts]]` layers contract (`containers=["breezy"]`, `exhaustive=true`) puts `runtime` **below** `strategy` with the explicit comment "Runtime never imports strategy" (`pyproject.toml:77-79`); `strategy` is documented as reaching **down** into `runtime` (`pyproject.toml:86-90`), never the reverse, and there is no existing `ignore_imports` entry for a runtime→strategy pair (`pyproject.toml:99-107`). A runtime-owned `catalog_day_ready` port calling into `composition.py` would therefore be a genuine layering violation, not a style nit — this is why the coordinator dropped it rather than merely deferring it. The one remaining catalog-adjacent code touched is the marker **text**, and per decision B its constant now lives in `runtime` (the lower layer) and `composition.py` imports it **downward** — the same direction the layering rule already permits (`strategy → runtime`, precedent: the backtest feed's shared `ClientId`, `pyproject.toml:86-88`).

## Root cause (measured, not assumed)

1. `NoTradableInstrumentsError` (`composition.py:166-171`) is raised at `composition.py:522` via `_zero_instruments_message` (`composition.py:406-415`), producing the literal `"current_rung_hold: resolved 0 instruments for <date> (<counts>); refusing to start"`. `app/trade.py`'s broad exception handler and `_report(...)` print this to stderr, and `spawn_node` redirects `stderr=subprocess.STDOUT` into the tailed node log — unconditional, independent of logging level (r1's finding, unchanged).
2. `_do_relaunch_check` classifies via `classify_exit1_cause` (`trade_supervisor_core.py:518-531`): `PERMIT_NOT_ISSUED_MARKER`→DETERMINISTIC, `TRADING_NODE_FAILED_MARKER`/`FATAL_*`→TRANSIENT, else UNKNOWN. The zero-instrument text matches none, so `decide_relaunch` (`trade_supervisor_core.py:549-570`) declines with `"exit cause is not transient"`.
3. **Structural finding (still the actual "whole day lost" cause):** `next_due`'s MIDDAY_WATCH branch (`trade_supervisor_core.py:1023-1028`) only fires when `effective.launch_done and effective.readiness_observed`. Once RELAUNCH_CHECK's budget exhausts with readiness never observed, `next_due` returns `Phase.NONE` for the rest of the day.
4. **New finding, not in r1 (drives decision C's exact routing):** `_do_relaunch_check`'s decline path returns `tracked_pid=None` (`trade_supervisor.py:1205`), but `_do_midday_watch`'s own decline paths deliberately return the **same, still-dead `tracked_pid`**, never `None` — its docstring states this explicitly: *"Contract, explicit and opposite of boot's ... this returns the SAME `tracked_pid` it was given, never `None`"* (`trade_supervisor.py:1250-1256`, enforced at `trade_supervisor.py:1308,1338,1359`). A boot-retry entry guard written as `tracked_pid is None` therefore fires exactly ONCE (the transition out of RELAUNCH_CHECK) and never again for any subsequent retry child that also dies — falling straight into the existing A-1 gate at `trade_supervisor.py:1320` (`if state.first_boot_permit_expires_at_ns is None:`), which fires `AlertDetail.MIDDAY_RELAUNCH_CEILING_UNKNOWN` and then returns the same dead `tracked_pid` forever, silently dead-ending the retry loop after its very first attempt. The correct, persistent "still in boot-retry territory" signal is **`state.first_boot_permit_expires_at_ns is None`** (a day-level anchor untouched by dead-child bookkeeping), not `tracked_pid`.
5. `disambiguate_exit_config_error`/`ExitConfigErrorCause` (`trade_supervisor_core.py:317-321,534-540`) is dead code — its only callers are its own two unit tests (`tests/unit/test_trade_supervisor.py:501-502,504-505`). Per decision I: **delete**, not re-wire.
6. Ingest cadence is `OnCalendar=*:0/15` (`deploy/systemd/breezy-quote-tape-ingest-frequent.timer:21`). The boot-time schedule itself budgets 15 minutes (`LAUNCH_UTC`=16:50 → `SELF_CHECK_UTC`=17:05, `trade_supervisor_core.py:34-35`) for a healthy boot to prove readiness — two independent 15-minute anchors already exist in this system, which is the evidence behind the retry cadence chosen below.

## Acceptance Criteria

1. A boot whose log carries the exact zero-instrument **refusal** marker (both `ZERO_INSTRUMENTS_REFUSAL_PREFIX` and `ZERO_INSTRUMENTS_REFUSAL_SUFFIX`, see Design) is latched `RelaunchCause.TRANSIENT`. A healthy node's `"skipping %s; resolved 0 instruments for %s"` warning (`composition.py:528-532,686-690`) and its `"... resolved 0 instruments for yesterday %s ..."` warning (`composition.py:693-698`) each classify `UNKNOWN`, pinned by a regression test — neither carries the suffix.
2. With `readiness_observed=False` at 17:00Z and a latched `boot_cause_seen=TRANSIENT`, `next_due` returns `Phase.MIDDAY_WATCH` from 17:10Z onward (not `Phase.NONE`).
3. With the same state but `boot_cause_seen` DETERMINISTIC or UNKNOWN, `next_due` still returns `Phase.NONE`.
4. There is **no catalog read anywhere in the retry path** (decision A). A boot-retry attempt is always spent when `decide_boot_retry` says eligible; a permanently-empty catalog therefore exhausts the fixed 3-attempt/15-minute-gap budget (~30-45 minutes after 17:10Z) and fires `BOOT_RETRY_ATTEMPTS_EXHAUSTED` CRITICAL — an explicitly accepted trade-off, not a defect.
5. Every spawn in the boot-retry path is gated by the same lock/PID/adoption precheck `_do_launch` already performs (`decide_launch_action`, `_attempt_adoption`) — never a bare `ports.spawn`.
6. Boot-retry's budget is its own counter: ≤3 attempts, **≥15 minutes apart**, never at/after `midday_watch_window_end` (01:00Z) — independent of `relaunch_attempts` and `midday_relaunch_attempts`. (Spacing raised from r1's 5-minute mid-day figure: 15 minutes matches both the ingest healing cadence and the system's own boot-to-self-check budget — see Root cause item 6 — so a retry always gets one full cycle of each before being re-tried.)
7. Attempt-budget exhaustion and window-close-while-never-ready each alert CRITICAL exactly once per day via distinct `AlertDetail` values. A retry child dying with a non-TRANSIENT cause alerts CRITICAL exactly once (`BOOT_RETRY_CHILD_NONTRANSIENT_EXIT`) and permanently stops the retry path for the day (AC13). Each precheck refusal (`REFUSE_LOCK_HELD`/`REFUSE_INTENT_OPEN`) inside the retry branch alerts its own distinct `AlertDetail`, unlatched per-occurrence — matching `_do_launch`'s own existing no-latch precedent for these two outcomes (`trade_supervisor.py:1079-1096`) — because the 3-attempt/15-minute budget itself already bounds frequency (AC14).
8. **Corrected from r1 (r1's AC8 was false):** a boot-retry child's readiness is tracked by the SAME `readiness_observed()` pure-predicate + `midday_readiness_recheck_done` machinery any mid-day-relaunched child already uses inside `_do_midday_watch`'s existing body (`trade_supervisor.py:1285-1308`) — **never** `record_readiness_observed`, whose only caller remains `_do_relaunch_check` (`trade_supervisor.py:1191`).
9. A boot-retry child mints its own, unrestricted first-boot permit exactly like a normal 16:50Z LAUNCH (`env=os.environ`, no `PERMIT_EXPIRY_CEILING_NS_ENV_VAR`) — never clamped, since no earlier boot succeeded today.
10. Once a boot-retry child's permit-issued line is observed, `record_first_boot_permit_seen` latches `first_boot_permit_expires_at_ns` (the existing per-poll call already at `trade_supervisor.py:1266-1271`), and from that poll onward **every** subsequent poll routes to the pre-existing mid-day-relaunch path — never back into the boot-retry branch. A later relaunch of this now-anchored child is capped by A-1/`decide_midday_relaunch`'s own existing budget exactly as any ordinary mid-day-relaunched child is, pinned by a test.
11. No file under `strategy/current_rung_hold/{decision,exit_decider,exit_authorization,tick_eval}.py`, `runtime/order_enablement.py`, or the A1 halt read path changes.
12. New `AlertDetail`/state fields are pure additions. There is **no existing exact-set pin** over `AlertDetail`/`RelaunchCause` to widen — only `CheckAlertDetail` is pinned (`tests/unit/test_alert_egress.py:29,218-219`), and it is untouched by this plan (decision K).
13. A retry child that boots and reaches readiness is still gated by the operator A1 halt exactly like any other node; a `boot_retrying`/`boot_retry_*` log or alert line must never be read as "trading resumed" (decision J).
14. `lint-imports` (run with `PYTHONPATH=<worktree>/src`, per the worktree lesson) passes after every change: `composition.py`'s new import of the two marker constants from `breezy.runtime.trade_supervisor_core` is a `strategy → runtime` "reach down," the direction the layers contract already permits; no file under `runtime/` gains an import of `strategy`/`composition.py` (decision K).

## Edge Cases & NFRs

- **Duplicate-boot / adopted-live-node race:** the retry branch reuses `decide_launch_action`/`_attempt_adoption`, never `ports.spawn` directly — identical protection to `_do_launch`'s own.
- **Stale dead-pid dead-end (root cause item 4):** the retry branch's entry guard is keyed on `state.boot_cause_seen is RelaunchCause.TRANSIENT and state.first_boot_permit_expires_at_ns is None` — **not** `tracked_pid is None` — so a second, third, etc. dead retry child (whose `tracked_pid` `_do_midday_watch`'s own convention keeps non-`None`) still routes correctly. "No live child" is checked internally (log read + `ports.process_alive`) as the first thing the retry helper does, not as an external routing precondition.
- **Permanent zero-instrument day:** no catalog check exists in this design (decision A); the day fails closed via ordinary attempt-budget exhaustion (~30-45 min after 17:10Z) rather than a separate "catalog never ready" signal — an explicit, accepted simplification.
- **Precheck-refusal thrash (decision F):** an attempt is consumed (`record_boot_retry_attempt` called) **whenever `decide_boot_retry` says eligible**, regardless of whether the subsequent precheck ultimately spawns, adopts, or refuses — so a persistent `REFUSE_LOCK_HELD`/`REFUSE_INTENT_OPEN` condition is re-probed only once per 15-minute slot, never once per supervisor poll tick.
- **Non-transient child re-exit (decision D):** once a retry child's own `classify_exit1_cause` comes back non-TRANSIENT, the retry path alerts once and permanently stops for the day; the pre-existing A-1 gate (`first_boot_permit_expires_at_ns is None`) will independently also fire its own once-per-day `MIDDAY_RELAUNCH_CEILING_UNKNOWN` the next time the (now bypassed) existing body is reached — a documented, accepted minor overlap, not new scope.
- **Supervisor restart mid-retry-window (decision H, non-goal):** `DaySchedulerState` is in-memory, rebuilt on restart (`trade_supervisor.py:1973`) — a restart after 17:10Z resets `boot_cause_seen`/`boot_retry_attempts` to their initial values, and an in-progress retry sequence is simply forgotten (any live retry child, if one exists, is adopted normally via `_do_launch`'s own restart path, outside this plan). Pinned by a test, not solved — the same accepted limitation `relaunch_attempts`/`midday_relaunch_attempts` already carry today.
- **A1 halt / operator caps:** orthogonal, untouched; see AC13/decision J.

## Design & Data Flow — options considered

- **(a) Marker→TRANSIENT only, retried inside the existing RELAUNCH_CHECK budget.** Insufficient alone (unchanged from r1): bounded to a ≤10-minute window that closes before most observed lags heal, and does nothing about `next_due`'s structural gate.
- **(b) Gate relaunch on catalog readiness (r1's recommendation).** **Rejected outright, not merely "insufficient standalone" as r1 said:** implementing it requires a runtime-owned port reading `strategy/current_rung_hold/composition.py`'s catalog helpers, which is a `runtime → strategy` import — forbidden by `pyproject.toml:69-97`'s exhaustive layers contract (see L-1 verdict). It also carried r1's own flagged MEDIUM-confidence station/day-manifest resolution gap. Both problems disappear by dropping it.
- **(c) Ingest-completion event triggers a relaunch.** Rejected (unchanged from r1): no native hook, new coupling/failure mode, violates YAGNI when the supervisor already polls everything on a steady cadence.
- **Recommended: cause-gated + fixed-cadence-and-budget-gated retry, inside the existing MIDDAY_WATCH window, no catalog read.** Cause-gated exactly as r1 (only zero-instrument-classified TRANSIENT boots enter this path, closing the R7b gap safely). Cadence-gated instead of readiness-gated: `decide_boot_retry` uses its own fixed 15-minute/3-attempt budget with no `catalog_ready` parameter at all — the 15-minute spacing is chosen because it is the smallest interval that lets **both** a fresh ingest cycle (`*:0/15`) **and** a fresh self-check window (15 minutes, `LAUNCH_UTC`→`SELF_CHECK_UTC`) complete between attempts, so no attempt is wasted re-probing a catalog/boot state that hasn't had a chance to change. This needs no new port, no new I/O surface, and no layering change — it is a pure extension of the existing `decide_relaunch`/`decide_midday_relaunch` pattern with one fewer input.
