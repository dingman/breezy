## ADM-1 — Σq does not count committed-but-unrecorded legs (verdict b: the latch does NOT serialize)

**The window.**
1. The create path writes the fill record (`exec/client.py:4385`), retires the intent (`:4408`), then emits `OrderFilled` (`:4419`).
2. `LiveExecutionEngine.process` queues that event, so the strategy's `on_order_filled`, and with it the TAKEN record in `_consume_or_flag_duplicate` (`continuous_strategy.py:3170-3189`), runs on a later loop turn.
3. In between, a sibling rung's depth frame passes the `:1920` pre-filter, because `is_intent_open()` is False.
4. IN_FLIGHT is keyed per instrument (`trial_day_latch.py:855-864`), so it does not block the sibling.
5. `station_day_admission` skips leg A because it has no trial record (`trial_day_latch.py:1543`, `raw is None`), so A's q is uncounted.

The resolver path has the same shape (`:2468` → `:2500` → `:2518`). Commit 97a6995 wired Σq into YES but does not cover this window.

**Acceptance criteria.**
1. Inside the window, a sibling whose total Σq > 1 is refused `station_day_admission`.
2. A leg with both a TAKEN record and a fill record is counted once, from TAKEN.
3. A no-fill IN_FLIGHT leg counts 0.
4. A fill whose fee is unknown or zero makes q unknown, so the order is refused (the existing `fee is None` rule).
5. A YES-only day is never refused.

**Change.**
- `trial_day_latch.py:1488-1555`: add a trailing kwarg `pending_fills: Mapping[str, DurableFillRecord] = {}`. When a leg has no trial record but does have a pending fill, compute `be = (cumulative_cost + cumulative_fee) / cumulative_qty` and add `_cell_probability(be, side)`. Verify units: USD per contract.
- `continuous_strategy.py:2143-2161` (YES) and `:2550-2568` (NO): collect the fill records already iterated and pass them as `pending_fills`. A shared helper removes the duplication.

**Tests.**
- `test_a_committed_fill_without_a_taken_record_counts_toward_sigma_q`. RED: returns None today. Also cover the double-count, zero-fee and no-fill in-flight cases.
- A fill-wiring test: retire A, write its fill, hold back `OrderFilled`, then send a depth frame for sibling B. Assert B is not submitted and is refused. RED: B is submitted today.

**Risks.**
- Refusal-only and millisecond-scale. It does not touch the permit or the budget, and the firewall is unaffected.
- The pending q uses the realized price, while TAKEN uses the ask at decision time.

**Alternative for the reviewers to weigh.** Refuse any leg that is IN_FLIGHT-open and has no trial record. The liveness risk: `_release_stale_inflight` runs only on that leg's own ticks.

## SP-3r — `_has_durable_fill_record` stub
**Current behaviour.** The stub (`client.py:1698-1701`) always returns False. Its only caller is `reconcile_at_startup` (`submit_intent.py:468`) at boot.

**Consequence.** A crash between `record_fill` and `_retire` reboots with the intent OPEN. Every order is then WAIT-denied, the create path leaves nothing for the resolver to pick up, and the operator has to run `clear_submit_intent`. This can only happen through a kill or crash, since that section has no await. Severity LOW.

**Constraint.** `intent_fingerprint` (`submit_chain.py:248-259`) hashes price and TIF. `DurableFillRecord` stores neither, so the fingerprint cannot be recomputed from the fill store.

**Acceptance criteria.**
1. After a crash between `record_fill` and `_retire`, the reboot retires the intent with `STARTUP_FILL_RECORD_MATCH`.
2. No index, a fingerprint mismatch, or a store error leaves the intent OPEN. A store error is caught, logged, and returns False.
3. The probe returns the literal True (the caller checks `is True`).

**Change.**
- Add `FILL_BY_FINGERPRINT_KEY_PREFIX` (near `:388`).
- After a successful `record_fill` and before `_retire`, write `<prefix><fingerprint> → venue_order_id`, always after the fill record. The create path uses `intent.fingerprint`; the resolver path uses `current_open().fingerprint`. A write failure goes to the existing `_FILL_WRITE_FAILED` refusal.
- The probe returns True only if the index entry's fill record exists and decodes.
- No change to the `DurableFillRecord` schema.

**Tests.**
- `test_a_committed_fill_with_an_open_intent_is_retired_at_boot`. RED: the intent stays OPEN today.
- Negative cases for acceptance criterion 2.
- Crash injection: make `_retire` raise, then run `_connect` on a fresh client.

**Risks.** This touches order re-enabling at boot. The budget is still seeded from durable fills afterwards (`:1672`), and the permit is untouched. Needs security review.
