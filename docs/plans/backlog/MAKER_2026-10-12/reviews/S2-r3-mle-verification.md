## Findings
**F1 [HIGH] Spec 6.0 sample floor dropped; "Spec input 2" is false.** Plan L59 (S-4) and L261 say v0.3 sets no minimum Stage 0 sample and a small non-empty sample "still gets a verdict". Spec L222-224: "A verdict requires the S1 station-day floor (effective n >= 30 climate-date-adjusted); below it Stage 0 emits UNDERPOWERED-WAIT with its n and interval, and no build starts." The pre-freeze tape gives ~8 dates x 4 stations (plan L67): effective n (climate-date-clustered, 4 stations share weather) is far below 30. As written S2 would emit a point-estimate NO-GO that S-1 treats as programme-terminal on ~8 independent clusters. S1 gates only its own censused count; S2's covered bid-bearing subset is smaller and can fall below the floor independently.
Fix (exact): (a) add row V0 to 1.1: "covered bid-bearing station-days with climate-date-adjusted effective n < 30 -> `UNDERPOWERED-WAIT` (n, n_eff, interval printed; V1-V5 still printed as descriptive, not as label; S-1 does not fire)". (b) WP5 computes n_eff = n / (1 + (m-1)*ICC-bound) using the same estimator S1 uses (cite S1 WP; do not invent a second one) - or by climate-date cluster count if S1 gives none. (c) Replace S-4 and Spec input 2 text with the spec L222-224 rule. (d) E1: require S1's verdict not UNDERPOWERED. (e) RED test `test_below_effective_n_floor_is_underpowered_wait_not_no_go`.

**F2 [MED] Heterogeneous process schedule makes the sample non-uniform (L124).** Logged relaunch cuts are added only on days whose node logs exist; other days use the nominal schedule (no relaunches), which yields fewer queue resets and a higher fill rate. The mix therefore depends on log retention, not on the strategy. Partial-day node outages are not simulated while full-day outages are dropped (L124 "non-bid-bearing") - the drop rule is undefined.
Fix: pre-declare PRIMARY = nominal schedule for every day (uniform, outcome-blind); logged-relaunch overlay = a second, report-only run on log-bearing days; verdict uses the stricter if they disagree on V1/V3 only (state it before the run). Define "full-day outage" = no node boot/permit line inside [16:50Z, 02:50Z); report the count and the day list; they are excluded from numerator AND denominator symmetrically. Pin the consumed node-log files (path, size, sha256, byte range) in `pins.json` (F4).

Plan L214 asserts "fit splits <= 2026-06-30" from `DEFAULT_SPLITS`. **F5 [MED] Leak-safety of forecast availability vs the live actor (L221 UNVERIFIED).** The 07Z note is nearly moot: a 07Z D-1 cycle (available ~08:10Z) is 8 h-stale by ~16:10Z, before the 16:50Z launch, so it never feeds a replayed bid; a 07Z D cycle is after permit end. If the live actor had an extra cycle the replay lacks, the effect is pessimistic only through a late 13Z (max 137 min, i.e. valid by 15:17Z - still before launch), so effectively nil. State this. The real direction risk is the opposite: replay `available_at` is the HTTP Last-Modified/floor, whereas the live actor sees a cycle only after its poll plus fetch, and is blind during its own outages. That makes the replay OPTIMISTIC on forecast timing. Fix: report +60 min (already in P2) AND a poll-lag stress equal to the live actor's poll interval (read `nbm_quantile_actor.py` constants) as report-only; label the 07Z item "moot" with the arithmetic.

Freeze in the plan, before WP0: WP0 thresholds (0.9/0.1, 200/side - already frozen), the first-replayable-day rule, and the Delta rule (F7).
