# S5 r1 review — prediction-market-reviewer — 2026-10-12
Verdict: SOUND-WITH-CAVEATS — tooling plan is lean and reuses the right stats code, but the PREREG as sketched has a circular split, an unreachable entry bar, a vacuous adverse-selection PASS, and several places where losses or n can be quietly flattered; fix these in spec v0.3 / the PREREG draft BEFORE freeze.

## Findings (ranked)
1. [BLOCKER] §5 WP5 `split`, §8 — the 60/40 split is circular. "Last 40% of calendar days of the run" needs the run length, but the read date is "first date the holdout target is met", and the target depends on deff_dev (dev outcomes). Holdout start is undefined at freeze, so it can drift with dev results. Revisions make it worse: each revision restarts the clock, so 3 revisions at ~160 dev days each is ~500-900 days, not 230-320 (the 230-320 figure assumes zero revisions; §8 says so only in one clause). Required: pin at freeze either (a) a calendar `holdout_start_date` and `calendar_cap_date`, or (b) holdout = all post-freeze days with zero planned revisions (see "Sample clock" below).
2. [MAJOR] §2 E1 vs S-5 — entry bar "Stage 0 fill rate >= 0.1" is inconsistent with the clock. Station-days with >=1 position/day = 3.64*(1-(1-r)^2): r=0.1 -> 0.69/day -> ~290 holdout days -> ~720 total; r=0.3 -> 1.9/day -> 105 days -> ~262 total. For a ~330-day total cap (holdout ~130 d) you need r >= ~0.25. Also the binding unit is station-day n, not position n. Stage 0 rate is an optimistic simulation (displayed size is a lower bound), so the cap pinned "from the S2 rate" is biased short. Required: E1 threshold = computed feasibility (r such that target is met by cap at the lower end of S2's stressed rate), plus an outcome-blind power stop at ~day 60 (projected holdout n at cap < target -> INCONCLUSIVE-UNDERPOWERED, end early). Also label S-5 `INCONCLUSIVE_UNDERPOWERED`; do not report it as a FAIL of the hypothesis (still no PROPOSAL).
3. [MAJOR] WP4 `adverse_selection_test` / §6.9 — vacuous PASS. Three strata with ~70 filled positions each and p_YES ~0.02-0.06: expected losses ~1.4-4 per stratum, so rejecting "loss rate > 1.5x model" is essentially impossible. A test that cannot fail will PASS an adverse-selection loss. Also three strata tested with no multiplicity, and unfilled counterfactuals are scored from a model of non-fills. Required: pre-register a minimum-power rule (min expected losses, or a pooled stratified statistic), define PASS as "upper cluster-bootstrap bound of (filled loss rate - model p_YES) <= pinned margin" (an explicit non-inferiority), and report the achieved power; an unpowered test returns INCONCLUSIVE = gate 9 false, not PASS.
4. [MAJOR] WP2/WP3 — shadow has no fill feedback. Strategy keeps `resting` for would-be rests but never learns of a simulated fill; the scorer joins fills offline. After a simulated fill the live path would stop resting that rung, count it toward the 2-rung/8-position limits and `exclusive_bucket_conflict`; the shadow keeps rotating rungs as p_no changes, so scorer can see >2 filled rungs per station-day, adjacent/modal fills, or later fills the real bot would never take. Backtest path != production path. Required: define scoring rule (first fill per (station,day,rung) only; positions per station-day capped in fill-time order; later-selected rungs scored only if the cap is open at their fill time) AND run the S2 fill simulator inside the strategy (or replay `decide()` with fill state) so decisions are causal. Also `qty=1` makes "partial fills aggregate" moot; say so and drop it.
5. [MAJOR] WP5 `alpha_*`, WP4 `holm`, `bootstrap`: (a) gate 3 says "95% CI excludes 0"; nested alpha (programme 0.025, family share, /3 for revisions) implies CI level 1-2*alpha_final, i.e. tail ~0.4-0.8%. A percentile bootstrap at that tail with ~110-130 climate-date clusters is unstable; pin the level, interval method (BCa / studentised or day-block) and B. (b) Holm "over the revisions" is wrong in structure: only the last revision touches the holdout, so there is ONE holdout p-value; dev p-values are selection-contaminated. Correct structure is alpha_family/3 (Bonferroni) for the selected revision, no Holm. (c) The harm stop is a type-II/calendar device, not a FWER spend (it cannot create a false promotion); Q5's "both draw on RA-13" is arguable. Pin alpha_stop by power loss, and keep the full nested alpha for gate 3. (d) `register_hypothesis` (hypothesis_ledger.py:873) runs a SS6.1 power check that can return UNDERPOWERED_NOT_REGISTERED for a 200-position design; resolve in WP0, not at freeze.
6. [MAJOR] WP4 `stress_set` — signature `(positions, tape, truth)` cannot compute the +/-1 F quantile shift or theta=0.08: both change p_no, b_max and therefore the rest set and fills. The JSONL logs decisions, not the per-rung p_no vectors/books. Required: log the quantile vector and fee inputs per forecast release, and specify re-decide vs re-cost per stress; for "every stress net-positive" pin point estimate vs CI. By-month cells (~66 positions each) positive-point-estimate-for-all is a coin-flip gate; make by-month report-only or pooled.
7. [MAJOR] WP5 `sequential_stop`: (a) S_k uses iid Bernoulli variance; with climate-date clustering (deff up to 1.5 allowed) the harm boundary is anti-conservative -> early false STOP kills a good family. Inflate by deff_dev or cluster-aware variance. (b) `boundary_for` (group_sequential_boundaries.py:163) returns BOTH (b_eff, b_fut), each spending alpha symmetrically; the plan must say harm = b_fut (lower), and that the maker uses the module function directly, NOT the pinned `BoundaryArtefact` path (gs_boundary_artefact.py:269-272 hard-pins i_max=40, alpha=0.025). (c) Looks "every 10 completed positions": order by settlement timestamp, tie-break deterministic; say whether the tally restarts at a revision. (d) OBF at t~0.014 (10/n_max~700) needs z < ~-9; the stop is practically inert before ~25% info. In shadow no money is at risk, so its only payoff is calendar savings; simplest-path would drop it unless the spec's §4 stop is deemed binding. Q3: CONTINUE/STOP-only is acceptable for the holdout (one weak bit, can only terminate), PROVIDED no revision can follow a holdout-era look; run it on dev days with revisions allowed and on holdout days terminate-only.
8. [MAJOR] WP3 positions / WP5 `voids_rule`, `read_date_rule` — loss hiding. Positions past `truth_deadline` (D+14) without FINAL, and voids, are "reported separately and excluded from the win count" but the plan never says how they enter expectancy/G3, ROI, or n. Required: primary gate calc scores unresolved-past-deadline as LOSS (full bid+fee), voids at venue refund minus fee, and G3 must hold under that conservative scoring; also pin CLI/METAR conflict handling (11:00 ET) and `incomplete_day_rule` (node outage days dropped symmetrically, not by outcome); G7 coverage threshold must be a number.
9. [MAJOR] WP4 `design_effect` — clusters = climate date treats consecutive days as independent; high-temperature tail events are serially correlated over 2-5 days, and the 1-day purge is thinner than a position's life (rests from D-1 listing, truth at D+1). Effective n and CIs are overstated. Required: day-block (e.g. 5-7 day) bootstrap or a lag-1..3 autocorrelation sensitivity beside the climate-date result, purge >= position life (split by climate day, holdout rests begin after last dev truth), and note holdout season (spring-summer 2027) differs from dev (winter); calibration artefact is dated 2026-09-30 and frozen.
10. [MAJOR] WP3 baselines — (a) comparison unit unpinned: per fill, per eligible rung-day (unfilled = 0), or ROI on deployed capital. Per-fill flatters the maker (selection into cheap fills); pin per-eligible-rung-day and per-capital, gate on the stricter. (b) forecast-only baseline requires p_no - ask - fee >= 0.10; with the NO ask near 0.9+ it may trade almost never, and "maker beats baseline" is then vacuous. Require min baseline n or report "NOT COMPARABLE", not "beaten". (c) "must beat both" (spec §6.6) is not among the nine gates (§7.1-7.9); decide gate vs report-only in v0.3 and say which.
11. [MINOR] Q4 forecast age — pin before freeze whether age is from `cycle_runtime` or `available_at`. With 13Z/19Z/01Z cycles and 6 h limit the bids are cancelled ~07Z-13Z regardless, and the S2 simulator MUST use the identical rule or the S2 fill rate is not the shadow's. Implement literally, report cancel-by-reason counts.
12. [MINOR] WP5 `first_shadow_day` — "utc_committer_date+1d" is a UTC date, positions are per station-local climate day; define as climate_day >= date AND rest timestamp > frozen_sha commit time.
13. [MINOR] WP4 gates — G4/G6 rows are attestation rows; give each a machine value (alpha used, leakage count=0) not a bool.

## Sample clock (answer to charter)
Arithmetic is internally right: 7.3 rested rung-days x 0.3 = 2.2 pos/day; station-days 1.9/day; holdout needs max(200/2.2=91, 200/1.9=105, x deff 1.0-1.4 -> up to ~130) days; /0.4 holdout share = 228-325 days. It is right only for r=0.3 and zero revisions; at r<=0.2 it is >400 days and at r=0.1 ~720.
Legitimate v0.3 changes BEFORE freeze (conservative or structural, decided blind to any S5 outcome; record that S2 results were seen): (i) pin split by calendar dates, not run fraction; (ii) make planned revisions 0 and treat Stage 0 (08-30..09-25) as the only dev set, so all post-freeze days are holdout (~91-130 days, the spec's "~100"); any later change is a NEW PREREG version with fresh holdout start and alpha re-split, never an edit (fork, not amend); (iii) outcome-blind power stop. NOT legitimate: lowering 200 or dropping the station-day/deff condition to fit the calendar, or choosing the dev fraction after seeing fill rates. Caveat: Stage 0 is small and B-3-disclosed, so with zero revisions the parameters ARE the spec's v0.2 constants and that must be said.
