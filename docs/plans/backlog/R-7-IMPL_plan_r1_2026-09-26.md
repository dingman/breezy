Evidence bytes and ordering are unchanged.

**`_match_position_lag`** (sync, pure except `_log`). Per pending entry:
1. Run the guard (§3).
2. If `read_ts ≤ recv_ns`, skip. The refresh `now_ns` is taken before the GET (`:1967`).
3. If the instrument is in `_position_lag_last_long`, emit `PRIOR_LONG`.
4. LONG check: pure `parse_position_status_report` with slug from `instrument_id_to_slug`, requiring not expired, `position_side == LONG`, and `mapped.leg == leg_of(id)`. Never call `_map_position`, which has side effects. An undetermined result stays pending.
5. If LONG: build the record, log it, pop the entry. Otherwise increment `reads_without_long`.
6. If `read_ts − recv_ns > _POSITION_LAG_PENDING_TTL_NS` (30 min), pop and emit `UNCONFIRMED_TTL`.
7. Recompute `_position_lag_last_long`.

**Lifecycle.** Pending entries are in memory only, lost on restart, and bounded (L-29). Resolver-path fills never create an entry.

## 3. tsEvent guard
- **Absent:** `parse_fill_report` requires `transactTime`, so its absence goes to AMBIGUOUS and no entry is created. As a second defence, `fill_ts_event <= 0` is rejected as `TS_EVENT_ABSENT` (L-17).
- **Skew bound:** `_FILL_TS_EVENT_MAX_SKEW_NS: Final[int] = 2 * 1_000_000_000`. This is build-side, not operator-reserved.
- **Evidence for the bound:** a read-only log grep covering the 8 create-path fills (09-13×1, 09-15×4, 09-21×2, 09-22×1). `transactTime` came 21–83 ms before local receive, never after it, and 115 ms–3.16 s after the preceding event. All 8 fall inside `[send, recv]` with zero overshoot. 2 s is ≤1.7% of the 120 s floor.
- **Reject line** (WARNING): `R7_LAG_REJECT reason=<TS_EVENT_ABSENT|TS_EVENT_SKEW_FUTURE|TS_EVENT_SKEW_PAST|PRIOR_LONG|MULTI_FILL_PENDING|UNCONFIRMED_TTL|MATCH_FAILED> instrument_id=… client_order_id=… fill_ts_event=… send_ns=… recv_ns=… bound_ns=…`
