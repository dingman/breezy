# FC-0a: NBS `txn` occupancy measurement -- settling P1's window shape

Generated by a single live run of `scripts/venue/iem_mos_txn_occupancy_probe.py`
(`IemMosProbeTransport`, paced >= 1 req/s, `IEM_ALLOWED_HOSTS`-only, GET-only,
per-request budget). Raw captures: `docs/evidence/iem_mos_txn_occupancy_probe_20260919T140753Z/`

## Why this measurement was needed

WP-1's reachability probe (`docs/evidence/iem_mos_reachability_probe_20260919T133522Z/`)
recorded `sample_row_1`/`sample_row_2` per year-cell -- the first two CSV data
rows for each `(station, model, year)` fetch. All 48 of those samples sit at
`ftime` 06:00 or 09:00 (confirmed by inspection of the 48
`nbs_*.summary.json`/`gfs_*.summary.json` files: every `sample_row_1`/
`sample_row_2` has `ftime` ending `06:00:00` or `09:00:00`), because a MOS
year-cell's CSV is sorted by `runtime`, then `ftime` ascending, so the first
two rows of any cycle are always its shortest projections. `txn` is a
period-aggregate (a daily max or min), populated only at the `ftime`s where
that period closes -- so WP-1's sample rows could never have shown it, whether
or not `txn` is populated elsewhere in the same file. WP-4
(`docs/evidence/FC_0a_4_PHASE_B_CLIMATE_DAY_FREEZE_2026-09-19.md`) inherited
that blind spot and could only record P1 as partially confirmed. This document
replaces that non-answer with a full-file census.

## P1 verdict: REFUTED as currently frozen -- the window ends at 00Z or 12Z, never 06Z

`scripts/analysis/forecast_climate_day_map.py` currently freezes:

```python
TXN_MAX_PERIOD_END_UTC_HOUR: Final[int] = 6   # INFERRED / RE-VERIFY
TXN_MAX_PERIOD_HOURS: Final[int] = 18          # INFERRED / RE-VERIFY
```

and `climate_day_for_txn` hard-refuses any row whose `ftime` UTC hour is not
exactly `6`:

```python
utc_hour = (ftime_ns // _NS) % _SECONDS_PER_DAY // _SECONDS_PER_HOUR
if utc_hour != TXN_MAX_PERIOD_END_UTC_HOUR:
    raise ForecastValidPeriodError("not the daily-max TXN period")
```

**REFUTED.** Across 14,720 real NBS rows spanning 40 days x 4 stations, `txn`
is non-empty at `ftime` hour 00Z or 12Z in every single case (3,520 populated
rows total), and at `ftime` hour 06Z in **zero** cases. `TXN_MAX_PERIOD_END_UTC_HOUR
= 6` does not match either of the two hours the venue actually publishes `txn`
at. As written, `climate_day_for_txn` would raise `ForecastValidPeriodError`
on **every** real live NBS `txn` row -- the frozen map cannot currently accept
a single genuine forecast value from this feed. (It is worth noting this is
consistent with, not contradicted by, WP-4 Phase B's CLI-truth alignment
script: that script only ever *constructs* synthetic `(runtime, ftime)` pairs
at `ftime=06Z(D+1)` by hand and checks internal consistency of the map
function against itself -- it never fetches or reads a real NBS row, so it
could not have caught this.)

The corrected picture, directly from the occupancy pattern:

- There are **two** separate daily-extremum periods, not one, and the map
  needs both a MAX case and a MIN case (see next section) -- the current
  single-constant design (`TXN_MAX_PERIOD_END_UTC_HOUR`, singular) is itself
  the wrong shape for what the venue publishes.
- The MAX period's `txn` is carried at `ftime` = **00Z**.
- The MIN period's `txn` is carried at `ftime` = **12Z**.
- The **period length** (how many hours the aggregation window spans before
  each end hour -- 12h vs 18h vs something else) is **UNVERIFIED** by this
  measurement. Occupancy census tells you *when* `txn` is published, not what
  interval of underlying observations it aggregates; confirming the exact
  span would require correlating `txn` against the hourly `tmp` element (or
  an independent truth source) within the same file, which this measurement
  did not do. Do not carry the existing `18` forward as if it were confirmed
  for the corrected end-hours -- it is exactly as unverified as `6` was.

## Max vs min disambiguation

**The rule is the `ftime` UTC hour itself, not `xnd`.**

Evidence -- mean `txn` value at each populated `ftime` hour, all 4 stations,
n=440 each:

| station | mean txn @00Z (n=440) | mean txn @12Z (n=440) | delta |
|---|---|---|---|
| KLAX | 79.5 | 67.8 | +11.6 |
| KMDW | 81.3 | 67.5 | +13.7 |
| KMIA | 91.9 | 79.6 | +12.3 |
| KSFO | 71.9 | 58.3 | +13.6 |

`ftime`=00Z is consistently and substantially warmer than `ftime`=12Z, by
11.6-13.7 F, at all four stations independent of local UTC offset (KMIA
UTC-5, KMDW UTC-6, KSFO/KLAX UTC-8). Converting to local standard time: 00Z is
local afternoon/early-evening at all four stations (KMIA ~19:00, KMDW ~18:00,
KLAX/KSFO ~16:00-17:00), and 12Z is local early morning (KMIA ~07:00, KMDW
~06:00, KLAX/KSFO ~04:00). That is exactly the afternoon-high /
overnight-low shape a MAX/MIN pair should have. **Rule: `ftime` UTC hour ==
00 identifies the daily MAX; `ftime` UTC hour == 12 identifies the daily
MIN.** Confirmed by physical magnitude and direction, independently at all
four stations, not by any label in the data.

Real rows (same runtime cycle, KLAX):

```
MAX: runtime=2026-08-10 18:00:00 ftime=2026-08-12 00:00:00 txn=78.0 xnd=1.0
MIN: runtime=2026-08-10 18:00:00 ftime=2026-08-11 12:00:00 txn=68.0 xnd=1.0
```

**`xnd` does NOT carry the max/min flag** -- this was checked directly and
refuted, not assumed. `xnd` takes small positive-integer-like string values
(`"1.0"` .. `"7.0"` observed). If it encoded MAX vs MIN, its value set would
partition cleanly between the `ftime`=00Z and `ftime`=12Z populations; it does
not:

| station | xnd values @ftime=00Z (MAX) | xnd values @ftime=12Z (MIN) |
|---|---|---|
| KLAX | {1.0: 307, 2.0: ..., 3.0, 4.0} | overlapping same set |
| KMDW | {1.0..7.0} | overlapping same set |

(Full counts in `TXN_OCCUPANCY_SUMMARY.json`, `xnd_value_counts_for_nonempty_txn`
per station -- computed only over rows where `txn` is populated, so these are
already restricted to the relevant rows.) `xnd` also does **not** equal the
calendar-day offset between `runtime` and `ftime` (directly tested: for KLAX,
only ~35% of populated rows have `int(xnd) == (ftime.date() - runtime.date()).days`,
and the mismatches are not a rounding artefact -- e.g. KLAX runtime
2026-08-11T12:00 carries four consecutive populated periods at `xnd=1.0`
before switching to `xnd=2.0`, not one-per-period). Cross-station, the same
`(runtime, ftime)` pair carries a *different* `xnd` at each station (e.g.
runtime=2026-08-10 18:00, MAX ftime=2026-08-12 00:00: KLAX `xnd=1.0`, KMDW
`xnd=3.0`, KMIA `xnd=1.0`, KSFO `xnd=3.0`), which rules out `xnd` being a
fixed property of the period itself.

**UNVERIFIED: what `xnd` actually encodes.** It is not MAX/MIN and not a
simple day-offset; nothing in this measurement determines its true meaning,
and Breezy's forecast pipeline must not read it as a disambiguator. The
`ftime`-UTC-hour rule above is the one to use, and it is independently
confirmed by physical magnitude at all four stations.

## What is settled vs what is not

| Question | Verdict |
|---|---|
| Is `txn` populated at all in live NBS? | **YES** -- 3,520/14,720 rows (23.9%) overall; 91.7% of rows AT the two hours it is ever published. |
| Is the occupancy pattern structured or scattered? | **STRUCTURED** -- exactly two `ftime` UTC hours (00Z, 12Z), identical across all 4 stations. |
| Is `TXN_MAX_PERIOD_END_UTC_HOUR=6` correct? | **REFUTED.** Real end-hours are 00 (MAX) and 12 (MIN); 06 never occurs. |
| Is `TXN_MAX_PERIOD_HOURS=18` correct (for the corrected end-hours)? | **UNVERIFIED.** Occupancy census cannot determine period length; not re-derived here. |
| How is MAX distinguished from MIN? | **`ftime` UTC hour** (00Z=MAX, 12Z=MIN), confirmed by consistent magnitude/direction at all 4 stations. NOT `xnd`. |
| What does `xnd` encode? | **UNVERIFIED.** Confirmed NOT max/min, NOT a simple day-offset. |

## Is the forecast family's core field usable from this source?

**Yes, but the frozen climate-day map is currently wrong and must not be used
as-is.** `txn` IS reliably published by live NBS, at very high occupancy
(91.7%) at its two true publication hours, at all four target stations, so
the field itself is usable. But `climate_day_for_txn` as currently coded
(`TXN_MAX_PERIOD_END_UTC_HOUR=6`) rejects every real value this measurement
observed -- it needs a code change (separate MAX-case and MIN-case end hours,
00Z and 12Z respectively) before it can accept a single live row, and the
period-length constant (currently `18`) needs independent re-verification for
whichever end-hour(s) it is paired with. That fix and re-verification are out
of scope for this measurement (a pure census); this document's job was only
to prove the assumption wrong with evidence and hand the corrected shape
(00Z/12Z, not 06Z; two cases, not one) to whoever picks up the fix.
