## 4. Coordinator follow-ups

**(e) sync-vs-resting.** The venue's own best practice (`overview_2026-08-25.md:343`) says do NOT use `synchronousExecution: true` for resting limit orders: the call blocks up to `maxBlockTime` (docs cap 10 s) waiting for a terminal state that a resting order will not reach, so the response at timeout is, by construction, a non-terminal order — and the docs do not specify whether that response carries `executions: [EXECUTION_TYPE_NEW]` or `executions: []`. The repo's existing IOC classifier already treats "empty executions at maxBlockTime" as AMBIGUOUS. Implication for WP1/WP4: a resting POST should be **asynchronous (default)** and immediately followed by `GET /v1/order/{id}` (poll ~100 ms per docs) and/or the private-WS `SUBSCRIPTION_TYPE_ORDER` stream, with `KIND_ACCEPT_RESTING` keyed on `state == ORDER_STATE_NEW` from the GET, not on the create response's `executions`. If WP1 keeps `synchronousExecution=true` for shape parity with IOC, the create response for a rest is UNVERIFIED and must be classified AMBIGUOUS-until-GET, never ACCEPT. WP6 must record the actual sync response shape for a rest at `maxBlockTime=5`.

**(g) HALTED forbids cancel.** The reference-data doc defines `HALTED` as "Like SUSPENDED, no cancels allowed" and `SUSPENDED` as cancel-only (`list-instruments_2026-08-25.md:159-162`). Implications for WP4c (per-order cancel) and WP4e (slug-scoped boot/stop sweep): (1) a cancel issued during a halt will be refused — the sweep must classify that refusal as **RETRY-WHEN-OPEN**, never as "no order to cancel" and never as a success; (2) the sweep's exit condition must be an empty `GET /v1/orders/open?slugs=...` re-read, not a 200 on the cancel POST (`canceledOrderIds` echoes the request and "do not certify that each ID was acted on" is the venue's own warning for batched cancels, `overview_2026-08-25.md:63-68`); (3) a market that moves HALTED -> EXPIRED/CLOSED expires resting orders venue-side ("All resting orders expired", `:165`), so an `EXECUTION_TYPE_EXPIRED`/`CANCELED` with `unsolicitedCancelReason` may arrive without any cancel of ours — the resting classifier must accept a venue-initiated terminal state as a valid retirement; (4) whether a halt itself cancels resting orders is UNVERIFIED and cannot be induced — WP4e should not rely on it. The retail market-level state enum that would gate the retry is `marketData.state` on `/v1/markets/{slug}/book` (`MARKET_STATE_HALTED` observed 09-05), since the market object's `status` was `MARKET_STATUS_OPEN` on 71/71 today and the instrument-state enum is institutional.
