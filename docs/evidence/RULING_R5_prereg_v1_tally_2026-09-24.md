## 3. Ruling

**(1) No — v1's 60/150 tally does not carry evidential weight for any family other than its own (`pm_us_crh_v2`), and it has not evidenced even that one.** It is superseded, not because a ruling redefines it, but because §7's own frozen text makes it structurally incapable of testing any successor: PREREG v2/v3/v4 are, by `assert_family_only`/`assert_live_only`'s enforcement plus each successor's own disjoint `trial_id_prefix`, separate families that "restart" `n` to 0 (§7 quoted above) and are never pooled with v1 rows. `pm_us_crh_v2` itself is REGISTERED, not un-registered, but has not been the sending family since `pm_us_crh_cont`'s D0 (2026-09-12) and carries n=0 for its entire measured history — it has never reached, and today shows no path toward, either the 60-dead or 150-survive floor.

**(2) Yes — `breezy-live-tally` may stop.** Retiring its **schedule** removes a unit that (a) has never produced non-zero evidence, (b) cannot by construction ever evidence the two REGISTERED families actually trading (cont/v4), and (c) duplicates, on a second daily schedule, a structural-dead check (`v1 section 5:105-106`) that `breezy-family-tally@pm_us_crh_v2` already performs against the same store, with its own alert edge. This is not a judgment that v1's design is wrong; it is that the unit is now redundant scheduling over an inactive family.

**(3) No — retiring the unit changes no PREREG semantics, and no §6 stop rule goes unmonitored.** §3/§5/§9's actual test (thresholds, BE formula, strata, BCa statistic) is not touched, edited, or deleted; `scripts/analysis/live_family_tally.py` and `mb_current_rung_edge_study.py` stay byte-frozen and remain runnable by hand; every produced artefact (`live_family_tally_*.md`, `live_tally.log`) is kept as citable history exactly as §8's artefact table requires. **Future artefact production under PREREG v1 §8 changes, and is justified rather than left unaddressed:** the nightly `live_family_tally_<date>.md` (§8's "Nightly tally (Markdown)" row) stops being produced going forward once `breezy-live-tally` is disabled — this is not a gap, because (i) PREREG v2 rev b `:13` already, validly, replaced the pooled statistic that report exists to serve (v1's fixed 60/150 Wilson rule) with the LD-OBF sequential design, so continuing to emit that report nightly would be n=0 boilerplate under a superseded rule; and (ii) the governing nightly artefact obligation continues to be met, uninterrupted, by `family_tally_v2_pm_us_crh_v2_<date>.md` (produced daily by `breezy-family-tally@pm_us_crh_v2`, §2 evidence above), which carries the same provenance elements §8 requires (source paths, row count, `as_of`, `manifest_sha256`) under the statistic PREREG v2 rev b actually governs by, plus the unchanged station/ask-band `cell_dead` check and the unchanged D0+165/ΣPnL≤−60 truncation clocks. If PREREG v1 §8 were read as obligating the LEGACY script's own report specifically (not merely "a nightly tally exists"), the correct disposition would be **keep** producing it — that reading is rejected here because §2 of PREREG v2 rev b (`:19-25`) explicitly preserves `live_family_tally.py`'s byte-identity as a frozen CODE PATH, never as a mandated ongoing SCHEDULE, and nothing in v1 §8 or v2 rev b binds the artefact's cadence independent of which statistic is currently governing.
