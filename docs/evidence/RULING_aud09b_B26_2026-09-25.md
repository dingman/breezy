## Question

AUD-09b-AMENDMENT §7 B26 (:132) reads: "Warm census plus one replay fits the unit (<900 s wall, <3 GB peak)". The evidence doc `AUD09B_B26_MEMORY_2026-09-25.md` reports two readings:

| Reading | What it measures | Result |
|---|---|---|
| A | cgroup `memory.peak` | census 11.0 GiB, replay 4.18 GiB (FAIL) |
| B | anon/RSS | 2.49 GB peak, 2.24 GB anon, 827 s / 900 s (PASS, narrowly) |

The question is which reading binds.

## Reconciled ruling

- **Binding metric.** "Fits the unit" is the operational bar. The run must complete inside the deployed caps (`MemoryHigh=3G` / `MemoryMax=4G`) with non-reclaimable anon below 3 GB and wall time below 900 s.
  - The rulers disagreed on which reading the text literally names. The architect said anon/RSS; the trading-bot-architect said the cgroup figure, page cache included.
  - Both agree the cgroup overshoot is reclaimable clean page cache (census file pages 9.05 GiB against 5.5 MB anon). Such cache throttles at `MemoryHigh` rather than getting killed.
  - So the observable cost of page cache is **wall time**, and the 900 s bar already governs that.
- **The evidence falls short of B26.** It has three gaps:
  - The census half was probably cold.
  - Both stages ran without the caps.
  - The only capped production run (10:27Z, 8 min 02 s) replayed a cheap day, MDW 09-01, rather than the heavy pick, LAX 09-17 (2.49 GB).
- **A non-BLOCKED step-13 row exists.** LAX 2026-09-01 is COMPLETED (`AUD-09b_replay_sufficiency_v2_census_2026-09-25.md`).

## Conditions

- **C1.** Merge `backlog/aud-09b-replay-bound-2026-09-25` (bounds `_select_capture_instruments` by station and warm-up start), then run the full gate.
- **C2.** In a quiet window, outside the node's hours and outside the nightly studies, start the real unit by hand (`systemctl --user start breezy-replay-daily.service`) on the census's own pick with a warm cache. Record all of the following:
  - journal `Finished` and no OOM;
  - census + replay wall time below 900 s, read from the unit's runtime line;
  - the row's `peak_rss_bytes` below 3 GB;
  - the journal "memory peak" line;
  - `MemAvailable` before and after the run.

  If wall time exceeds about 810 s, bound the census reads next (AUD-09a scope). Raising `MemoryHigh` needs its own review.
- **Then:**
  1. `systemctl --user reset-failed breezy-replay-daily.timer`
  2. `systemctl --user enable --now breezy-replay-daily.timer`
  3. Ratchet B5 (base plan §8 row :841, §7 step 14 :829-831) at 2× the C2 measurement, with the memory bound capped at `MemoryMax=4G`.

## Rejected alternatives

- **B5 at 2× the step-13 row** (156.9 MB, 61.4 s). That day was engine-only with zero trades, so it is a degenerate baseline. The known heavy day is already 15.9× it, and the very next heavy run would false-fail.
- **Treating B26 as FAIL on the cgroup reading.** That reading is page-cache inflated and does not measure whether the job fits.

## Residual risks

- **No automatic alert on B5.** B5 is a review bar only; nothing alerts when a run exceeds it. Wiring an alert is a follow-up.
- **Cold-cache runs are untested.** A run with no `instance_spans.jsonl` measured 5.9–6.0G under an older 6G cap. Under `MemoryMax=4G` it could be OOM-killed, and that case has not been tested. The unit's `OnFailure` alert is the detector.
- **Host memory pressure before node launch.** The node is deliberately uncapped. Replay page-cache churn ends at the latest by 16:20Z (`TimeoutStartSec`), 30 minutes before the 16:50Z launch. C2 records `MemAvailable` to cover this.
